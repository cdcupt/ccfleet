ccfleet Guidebook

00Every day

You open a web page. That is the whole thing. Claude Code runs on your node, not on the machine in front of you, so there is nothing to install, nothing to configure and no terminal.

To work

Open https://claude.ai/code, or the Code tab in the Claude mobile app, and pick your node's session. It is named after the node.

Work exactly as you would locally. Files, tools and git all live on the node.

To check your node

Open your console, the address your operator gave you. It shows status, Claude Code version, egress address, disk, login freshness and any alerts.

What you see depends on the login you were given. An owner login shows your own nodes and nothing to press; managing them is the operator's job. The operator's own login, or the admin token, shows the whole fleet and can add, disable and remove nodes. Section 06 has the detail.

Nothing depends on your laptop

The session runs on the node under a service that starts at boot. Close the browser, shut the laptop, change country, pick it up on your phone. The conversation is still there. The heartbeat agent, the tunnel and the nightly backup run the same way.

The one thing you do yourself

Signing in. Nobody can do it for you, by design: your subscription login must complete through Anthropic's own flow. It happens once per node, during setup, and after that the node refreshes its own credentials. The dashboard raises credentials_missing or token_expired if it ever needs doing again.

If you prefer a terminal

A terminal is optional, not required. If you want one, connect over SSH and attach to a persistent session so that closing the window does not end your work:

ssh <owner>@<node>
claude            # logging in already attached you to the persistent session

Detach with Ctrl+b then d, or just close the window. The session survives a disconnect. A reboot clears whatever was running inside it, but you do not have to create one again: the node re-creates the session at boot, so your next ssh still lands in it. Remote Control is enabled at boot too, so it comes back on its own.

01What you get

ccfleet manages several personal Claude Code installations without proxying their traffic or holding their logins. Each person gets a small hosted machine (a node) running the unmodified Claude Code CLI, signed in with their own subscription through Anthropic's normal login flow. A tiny agent on each node reports public facts to one fleet server, which draws a dashboard and sends alerts. That is the whole system.

Included

  • Node install: one command takes a blank server to ready-for-sign-in, hardened, with the agent reporting. The older bootstrap and owner-setup scripts remain for machines you manage by hand.
  • Node upkeep: staged upgrades and backups that exclude credentials.
  • Agent: one Python file, standard library only, systemd timer every five minutes.
  • Fleet server: dashboard, JSON API, alert rules, Telegram, node token management.
  • ccp: several accounts on one laptop, each in its own profile, switched by hand.

Deliberately absent

  • No relay or proxy for model traffic.
  • No storage of anyone's credentials; the optional gateway forwards an owner's own requests unchanged and keeps nothing.
  • No header or request rewriting, no fingerprint games.
  • No account pools, share links, seats or automatic failover between accounts.

Read this once

ccfleet keeps you inside the arrangements Anthropic documents: the unmodified Claude Code binary, signed in by its owner, hosted or not. It cannot change where you are. Anthropic's supported-regions list does not include mainland China, Hong Kong or Macau, and a node abroad does not alter that. The compliance notes in the repo quote the exact passages.

03Fleet server

The server is a single process: ccfleetd serve. It listens on loopback, stores everything in one SQLite file, and needs one secret, the admin token. Docker is the quickest path; a plain systemd unit is provided too.

1

Get the code and set the admin token

git clone https://github.com/cdcupt/ccfleet.git
cd ccfleet
cp deploy/ccfleetd.env.example deploy/ccfleetd.env
chmod 600 deploy/ccfleetd.env
openssl rand -hex 32        # paste as CCFLEET_ADMIN_TOKEN in deploy/ccfleetd.env

Set CCFLEET_PUBLIC_URL to the address you will put in front of it, so alerts can link to the dashboard.

2

Start it

# Docker
docker compose -f deploy/docker-compose.yml up -d --build
curl -s http://127.0.0.1:8110/healthz      # {"ok": true}

# or plain Python
pip install git+https://github.com/cdcupt/ccfleet
set -a; . deploy/ccfleetd.env; set +a
ccfleetd serve

For a permanent plain install, deploy/ccfleetd.service runs it as an unprivileged user under systemd; its header comment lists the four commands to set that up.

3

Put TLS in front

# deploy/Caddyfile.example
fleet.example.com {
    reverse_proxy 127.0.0.1:8110
}

Open the address in a browser. User name admin, password the admin token. You will see an empty fleet with the hint to add a node. That token is the operator's way in and always works; named logins for owners come later, in section 06.

No public endpoint?

You can skip the hostname, the DNS record and the certificate entirely. A node can reach the server through an SSH tunnel instead: a user service forwards a loopback port on the node to this server's loopback port, and the agent posts to its own 127.0.0.1 with SSH providing the encryption. ccfleetd's HTTP endpoint stays private, though the server does still need a reachable SSH port, which is the one surface this design depends on. See docs/tunnel.md in the repo.

4

Register each owner's node

Do this from the console once it is up: add the node, and the page that follows gives you an install command with the server URL, node id and token already in it. Append the owner's --ssh-key before you run it, or the installer skips SSH, firewall and fail2ban hardening rather than risk locking everyone out. Section 04 has the detail.

The token is shown once. Send it to the owner over a private channel, or run the install yourself. Lost it? ccfleetd node rotate-token node-a mints a new one and revokes the old one.

If that owner should be able to check their own node's health, give them a console login as well. Without one they have a node and no way to see whether it is alive:

docker compose -f deploy/docker-compose.yml exec ccfleetd \
  ccfleetd user add alice --owner alice

The password is generated and printed once. See section 06 for what that login can and cannot do.

5

Optional: Telegram alerts

Create a bot with @BotFather, send it one message, read your chat id from @userinfobot, then set CCFLEET_TELEGRAM_BOT_TOKEN and CCFLEET_TELEGRAM_CHAT_ID in the env file and restart. Test with:

docker compose -f deploy/docker-compose.yml exec ccfleetd ccfleetd alert-test

04A node per owner

One command, then one sign-in. The console prints a ready-made install line when you add the node; you run it once on a blank server as root and it takes the machine all the way to the sign-in. It cannot do the sign-in itself, because a subscription login has to complete through Anthropic's own flow, so the owner does that part and nobody else can.

1

Add the node and copy the command

Open the console, fill in the node id and the owner, and submit. The page that follows shows the token once, and an install command with the server URL, node id, token and owner already filled in. Copy it.

The copied command is missing one thing on purpose

The console cannot know the owner's public key, so the command it prints has no --ssh-key. Run it as-is and step 2 will skip SSH, firewall and fail2ban hardening altogether, on purpose, rather than disable password logins on a machine with no key on it and lock everyone out. Add the flag before you run it, or add a key and re-run afterwards.

If you prefer the terminal, the CLI does the same thing and prints the same three identity lines:

docker compose -f deploy/docker-compose.yml exec ccfleetd \
  ccfleetd node add node-a --owner alice --region us-west --rc-expected
  • --rc-expected makes the dashboard alert when the owner's Remote Control service is not running. Leave it out for owners who only use SSH.
  • --pinned-version 2.1.92 can be given now or set later with ccfleetd node pin.
  • Lost the token? ccfleetd node rotate-token node-a mints a new one and revokes the old one.
2

Run it on the blank server, as root

curl -fsSL https://raw.githubusercontent.com/cdcupt/ccfleet/main/node/install.sh \
  | sudo bash -s -- \
      --server https://fleet.example.com \
      --node node-a \
      --token <the 64-character token> \
      --owner alice \
      --ssh-key "ssh-ed25519 AAAA... alice"

It installs packages, creates the owner with a lingering session so their timers survive logout, hardens SSH and the firewall, installs Claude Code, pre-answers the two setup prompts that are not about anyone's account, installs the agent and its units, starts the work session and the timers, and posts a first heartbeat. It prints each step and refuses to call the machine ready if a service did not come up.

  • --ssh-key takes the owner's public key. Without it, SSH hardening is skipped on purpose rather than risk locking everyone out, and you must add a key yourself.
  • --skip-harden leaves the firewall and sshd alone. Use it on a box already carrying other services.
  • --no-remote-control sets up everything else and leaves Remote Control off.

Rerunning it is safe

Every step checks before it acts, so a second run repairs a half-finished install rather than duplicating it. If a service fails to start, the script exits non-zero and names the unit instead of reporting success.

3

The owner signs in

ssh alice@<node>     # you land straight in the persistent work session
claude

Choose the claude.ai login. Over SSH the browser cannot call back into the node, so Claude Code shows a URL: open it on your laptop, approve, copy the code the page shows, paste it into the terminal. Then check:

/status

The Login row must show your account. There must be no Anthropic base URL line and no Auth token or API key line. If there is, an environment variable is set that should not be; unset it and restart claude.

Where the login lives

On Linux, Claude Code keeps it in ~/.claude/.credentials.json with mode 0600 and refreshes it by itself. The agent parses this file only to pick out the expiry timestamp and plan type; the token values are discarded in memory and never sent, logged or stored, and the file's modification time is read from its metadata.

4

The owner turns on Remote Control, once

systemctl --user start claude-remote-control.service

After this, claude.ai/code and the Claude phone app can drive this node with nothing installed on the machine you are sitting at. tmux -L ccfleet-rc attach -t remote-control shows the URL and QR code.

Why the installer does not do this for you

Remote Control needs an authenticated session, and there is none until the sign-in above. The installer therefore enables the service, so it returns by itself after a reboot, but does not start it. It cannot usefully retry either: the unit runs Claude inside a detached tmux session, so systemd sees the launch succeed the moment tmux detaches and never learns that the session failed to authenticate. One command by the owner is honest; an automatic retry would not work.

5

Optional: off-node backups

The nightly backup already runs locally (~/backups/ccfleet, last 14 kept, credentials excluded). To copy archives elsewhere, install rclone, configure a remote, and create ~/.config/ccfleet/backup.env:

CCFLEET_BACKUP_REMOTE=r2:my-bucket/ccfleet/node-a
CCFLEET_BACKUP_EXTRA=/home/alice/projects

The long way round is still there, but it is not equivalent

If you would rather not paste a token into a command, the console also prints the three agent.env lines on their own. Run node/bootstrap.sh as root, then node/setup-owner.sh as the owner, and place those lines in ~/.config/ccfleet/agent.env afterwards. That order is not optional: the owner's account and home directory do not exist until the first script has run.

Those two scripts cover the packages, the owner account, sudo, the firewall, lingering, the helper binaries and the agent, backup and work-session timers. They do not do the rest, and you are taking it on yourself:

  • No fail2ban. bootstrap.sh does not install or configure it, so the node has no SSH brute-force protection until you add it.
  • Claude Code's two setup prompts are not pre-answered, so the owner meets them interactively.
  • agent.env is created, but from a template. The URL, node id and token in it are placeholders you replace by hand.
  • Remote Control is not enabled by the script. Its closing message tells the owner to do it, so until they do it will not return after a reboot.
  • Both scripts run under set -euo pipefail, so a unit that fails to start does abort them. Neither re-checks the units afterwards nor sends a first heartbeat, so a service that starts and then dies goes unnoticed until the dashboard misses it.

Section 04 above is the supported path. Reach for this one only on a machine you are managing by hand, and close those gaps deliberately.

05Laptop profiles with ccp

If you hold more than one account, keep each in its own Claude Code profile and switch explicitly. A profile is a separate CLAUDE_CONFIG_DIR: its own login, settings and history. Nothing is pooled and no session ever hops between accounts.

install -m 755 profiles/ccp ~/.local/bin/ccp
ccp add personal            # empty profile
ccp add work --share        # links your existing skills, agents, commands, settings.json and CLAUDE.md
ccp use personal            # runs claude under that profile; /login once
ccp list
PROFILE              ACCOUNT                      LOGIN      DIR
personal             e***@example.com             keychain?  /Users/alice/.claude-profiles/personal
work                 e***@example.org             keychain?  /Users/alice/.claude-profiles/work

On macOS the login lives in the Keychain (per profile), so ccp list can only say "keychain?"; on Linux it reports whether the credentials file exists. ccp env work prints an export line for scripts that need the variable set in the current shell.

06Daily use

Who can sign in

The console takes two kinds of credential.

CredentialSeesCan manage nodes
The admin token
user name admin, or any name at all		the whole fleetyes
ccfleetd user add NAME --role adminthe whole fleetyes
ccfleetd user add NAME --owner OWNERonly that owner's nodesno

An owner login is deliberately read-only. The management forms are not rendered for it, and that is only the cosmetic half: every write route checks the role, so a hand-built request is answered 403 rather than 401. Their credentials were fine; the action was not theirs.

Manage them with ccfleetd user list, ccfleetd user passwd NAME and ccfleetd user remove NAME. Passwords are stored as salted PBKDF2 hashes and cannot be recovered, only reset.

What this is not, yet

There are no sessions, so the browser holds the credentials for the realm until it is closed, and there is no self-service password change: resetting one is the operator's job.

Working on a node

  • Terminal: ssh alice@node or mosh alice@node. You land in the persistent session automatically, with no tmux command to remember. mosh survives laptop sleep and roaming.
  • VS Code: Remote-SSH to the node; the Claude Code extension runs there with the node's login.
  • Phone or any browser: claude.ai/code, pick the node's session (it carries the node's hostname).
  • Usage windows: type /usage inside a session on the node. Windows are per account; a second account is a second window, not a bigger one.

07Operations

Staged upgrades

Auto-update is off on nodes on purpose. Upgrade one node, work on it for a day, then roll the rest:

# on the node
ccfleet-upgrade-claude            # latest
ccfleet-upgrade-claude 2.1.92     # exact version
# on the server
ccfleetd node pin node-a 2.1.92

Rotate a node token

ccfleetd node rotate-token node-a
# then update the node's agent.env

The old token stops working immediately.

Rebuild a node

  1. New VPS, then the one install command from the console (rotate the token first, so the command carries a valid one).
  2. Restore the latest claude-state-*.tar.gz with tar -xzf claude-state-<stamp>.tar.gz -C / (archive paths are relative to /). It contains settings, projects and history, never credentials.
  3. Owner runs claude and /login.

Remove an owner

ccfleetd node disable node-b   # keep history
ccfleetd node remove node-b    # delete it all

The owner runs /logout on the node before it is destroyed.

The repo's docs/runbooks.md has one short procedure per alert, plus the quarterly reminder to re-read Anthropic's terms and gateway pages.

08Optional pass-through gateway

For an owner who cannot work on a remote filesystem, Anthropic's gateway docs describe a second permitted arrangement: Claude Code runs and logs in on the laptop, only ANTHROPIC_BASE_URL points at a gateway, and the saved claude.ai login stays the active credential. gateway/Caddyfile.example implements it: it requires a private header, drops that header, passes the body and Anthropic's required headers through unchanged with streaming on, and stores nothing. Like any reverse proxy it does set Host and add X-Forwarded-*; what it never does is substitute a credential or alter who the client says it is.

# laptop
export ANTHROPIC_BASE_URL=https://gw-a.example.com
export ANTHROPIC_CUSTOM_HEADERS="X-Gw-Key: <secret shared with the gateway>"
claude
/status      # base URL shows the gateway; Login row still shows your account

Two cautions

Never authenticate the gateway with ANTHROPIC_AUTH_TOKEN: that variable replaces the subscription as the credential. The Caddyfile has now been exercised against a live session: a real session completed through it, and stopping the gateway made the same command fail while restarting it made it work again, so it was genuinely in the path. That test ran over a loopback port through an SSH tunnel, so TLS termination and a public hostname are still unexercised; run a long streamed session over the real hostname before depending on it. One gateway, one owner, one account.
