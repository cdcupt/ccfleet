CC Fleet · guidebook · 2026-09-28

Claude Code anywhere, one account per slot

CC Fleet hosts the original Claude Code CLI in a private Linux slot. A small local command connects your terminal to it; the Claude credential and model traffic stay on the slot.

The invariant

One holder, one slot, one Claude account. CC Fleet never pools accounts, chooses an account for a request, or exposes a shared Claude API.

Customer experience

  1. Sign in to the CC Fleet website with Google and claim a slot.
  2. On the slot card, press Sign in to Claude. Complete Anthropic's own flow and paste its code back. The resulting credential is written on the slot only.
  3. Wait for In use, then press Connect this computer.
  4. Install and pair:
curl -fsSL https://raw.githubusercontent.com/cdcupt/ccfleet/main/laptop/install.sh | bash
ccfleet login

Paste the single-use code from the page. It expires after ten minutes.

On a computer that used the old ccfleet-connect token flow, replace both commands above with the migration command below. It installs and pairs first, then removes the old local setup only after pairing succeeds:

curl -fsSL https://raw.githubusercontent.com/cdcupt/ccfleet/main/laptop/install.sh \
  | bash -s -- --migrate

Revoke the old setup-token in the Anthropic account if nothing else uses it.

  1. Run ccfleet. The original Claude Code interface opens in the terminal. Run it again after a disconnect to resume the same session.

Projects and tools

Projects live in ~/workspace on the slot. Clone with Git or retrieve them from inside the slot. Shell tools run there through Claude Code. The local client does not mount or silently copy the computer's current directory.

Session choices

Hosted sessions start Claude Code with permission prompts off. The slot has no sudo, but Claude may read, change, delete or send anything the slot user can access without asking first. Users can create a separate session in a different mode, model and effort level:

ccfleet new research --model fable --effort xhigh --mode plan
ccfleet attach --session research
ccfleet restart --session research --model opus --effort max --mode auto

The supported modes are acceptEdits, auto, bypassPermissions, manual, dontAsk and plan. Effort levels are low, medium, high, xhigh, max and ultracode. Inside a session, /model and /effort change it without losing the conversation. Restart deliberately ends the current Claude process.

Connection path

user terminal: ccfleet │ TLS/WSS containing encrypted SSH ▼ BWH: CC Fleet broker │ opaque SSH bytes; fixed assigned endpoint ▼ slot: forced entry → persistent tmux → original claude │ ordinary Claude HTTPS under this slot's one account ▼ Anthropic

BWH authenticates the CC Fleet device token and chooses the operator-configured slot endpoint. It does not terminate the inner SSH session, so it cannot read terminal contents. The client pins the slot machine's SSH host key.

Privacy boundary

PlaceWhat it holds or can observe
User computerA CC Fleet device token, private SSH key, pinned host key and terminal data. No Claude credential.
BWH brokerThe device-to-slot mapping and connection metadata. It relays the inner encrypted stream and cannot read it.
SlotThe Claude credential, files, tools, prompts and responses. This is where Claude Code runs.
AnthropicThe ordinary traffic and metadata sent by Claude Code on the slot, under the customer's own account.

The slot machine's administrator has root and can technically inspect slot files or processes. Transport encryption does not hide data from the computer that executes it.

Server and machine setup

1. Deploy BWH

git clone https://github.com/cdcupt/ccfleet.git
cd ccfleet
cp deploy/ccfleetd.env.example deploy/ccfleetd.env
docker compose -f deploy/docker-compose.yml up -d --build

Configure the public URL, Google OAuth, cookie secret and admin token. Put TLS in front of the service. The product is at the bare URL, customers use /account, and operators use /admin.

CCFLEET_BYPASS_BY_DEFAULT stays off for hosted customer slots. Turning it on adds --bypass-permissions to legacy owner-node install instructions; because those owners also have passwordless sudo, use it only on a fleet you personally control.

CCFLEET_BROKER_ONLY defaults to false. Enable it only for a secondary broker sharing the primary database and secrets: it serves health and authenticated CLI transport, status and revocation, without account/operator pages or an independent monitor. See the broker Compose and Caddy examples in deploy/; a same-host replica does not protect against loss of the physical host.

2. Register one shared machine and slot

ccfleetd node add pool-1 --owner ops --region us-west
ccfleetd slot add pool-1 --machine pool-1 --unix-user slot01
ccfleetd node pin pool-1 latest

Keep the node token printed by the first command for installation.

3. Prepare the machine

git clone https://github.com/cdcupt/ccfleet.git
sudo ./ccfleet/node/bootstrap.sh ops "ssh-ed25519 AAAA... operator"
sudo hostnamectl set-hostname pool-1
sudo timedatectl set-timezone Etc/UTC

curl -fsSL https://raw.githubusercontent.com/cdcupt/ccfleet/main/node/machine-setup.sh \
  | sudo bash -s -- --server https://fleet.example.com --node pool-1 --token <node-token>

4. Configure the BWH-to-machine endpoint

Copy the node's /etc/ssh/ssh_host_ed25519_key.pub to a root-owned file on BWH over an authenticated operator channel, then:

ccfleetd node access pool-1 \
  --host <address reachable from BWH> \
  --port 22 \
  --host-key-file /secure/path/pool-1-host-key.pub

The customer never receives the node address. Only BWH needs network access to this port.

5. Grant a customer

ccfleetd account quota alice@example.com 1

The customer must have signed in to the website once before the account exists.

Verification checklist

  • The slot is not claimable until the machine heartbeat reports its Linux user absent.
  • After pairing, /etc/ccfleet/authorized_keys/slot01 contains a forced slot-entry.sh command. The sshd slot-group policy independently forces that entrypoint and disables agent, port and X11 forwarding and user rc.
  • The public-key path is readable but root-owned and not holder-writable; the machine token beside it remains in an atomic mode-600 file.
  • The slot account is public-key eligible, while effective sshd policy still reports passwordauthentication no and kbdinteractiveauthentication no.
  • ccfleet opens Claude Code without asking for a Claude login on the local computer.
  • Stopping BWH breaks a new connection; restarting it allows the same local profile to reattach.
  • Removing the device on the slot page closes its open broker connection, rejects new ones and removes its public key on the next agent cycle.
  • Releasing the slot revokes every device immediately and the slot is not free until the machine confirms the user and files are gone.
  • No customer documentation offers Remote Control, a Claude app mode, a device-token mode or an SSH command.

Daily commands

CommandPurpose
ccfleetOpen or resume the active slot.
ccfleet loginPair this computer with a code from the slot page.
ccfleet listList locally paired slots.
ccfleet use NAMEChoose the default when this computer has more than one slot.
ccfleet logoutRevoke this computer and remove its local key.
ccfleet new NAME --model MODEL --effort LEVEL --mode MODEStart a separate named session.
ccfleet attach --session NAMEResume a named session.
ccfleet restart --session NAME [choices]Deliberately replace its current Claude process.

Recovery

  • Claude sign-in expired: use Sign in again on the slot page. Do not send credentials to the operator.
  • Computer lost: remove that device from the slot page. Pair a new device with a new code.
  • Host-key mismatch: stop. Verify the machine was intentionally rebuilt, update its access configuration with the new public host key, and pair again.
  • BWH unavailable: the Claude/tmux process continues on the slot. Restore the broker and reconnect.
  • Slot machine unavailable: the broker returns a temporary-unreachable error; inspect the machine and its SSH reachability from BWH.
