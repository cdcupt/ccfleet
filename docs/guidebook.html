00Every day

You open a web page. That is the whole thing. Claude Code runs on your node, not on the machine in front of you, so there is nothing to install, nothing to configure and no terminal.

To work

Open https://claude.ai/code, or the Code tab in the Claude mobile app, and pick your node's session. It is named after the node.

Work exactly as you would locally. Files, tools and git all live on the node.

To check your node

Open your console, the address your operator gave you. It shows status, Claude Code version, egress address, disk, login freshness and any alerts.

What you see depends on the login you were given. An owner login shows your own nodes and one thing you can act on: signing your own node in. Everything else — adding, disabling, pinning, removing — stays with the operator. The operator's own login, or the admin token, shows the whole fleet. Section 06 has the detail.

Nothing depends on your laptop

The session runs on the node under a service that starts at boot. Close the browser, shut the laptop, change country, pick it up on your phone. The conversation is still there. The heartbeat agent, the tunnel and the nightly backup run the same way.

The one thing you do yourself

Signing in. Nobody can do it for you, by design: your subscription login must complete through Anthropic's own flow. It happens once per node, during setup, and after that the node refreshes its own credentials. The dashboard raises credentials_missing or token_expired if it ever needs doing again.

The CLI on your own machines

If you would rather run Claude Code locally — your own files, your own editor — you can, without signing in on each machine.

From the console, with no terminal. Open the dashboard, find your node under Device tokens, and press Get a device token. Your node mints one from the account it is already signed in as: a link appears, you approve it, you paste the code back, and the token is shown. You can show it again while the request lasts, so a second machine can have the same token; press Done with it when you have finished and it goes at once.

How long it stays readable

Until you press Done with it, or fifteen minutes pass and the attempt expires on its own — whichever comes first. Show it as often as you need in that window, which is what makes putting the same token on a second machine possible without minting another.

It was shown exactly once at first. That was stricter than anything required: the credential sits in the database from the moment the node reports it until the attempt expires either way, so reading it twice adds no exposure the first read did not. The window is what bounds this, not the reading. Press Done with it when you have finished and it goes at once.

Then, on each machine you want it on:

bash -c "$(curl -fsSL https://raw.githubusercontent.com/cdcupt/ccfleet/main/laptop/ccfleet-connect.sh)"

That is the whole setup on a new machine. It asks for the token, hides what you paste, and checks the token against Anthropic before writing anything at all — a refused token leaves the machine exactly as it was. Once the token is accepted it also installs itself to ~/.local/bin, so ccfleet-connect --status and --remove work later; if that part fails it says so rather than leaving you with a command that is not there. Run through bash -c rather than piped into a shell: a pipe takes the keyboard away from the prompt.

When it finishes it hands you a fresh shell with the token already in it, so claude works in that same window. A program cannot put a variable into the shell that started it — that is what a child process is — so the choice was between an export line to type by hand and a new shell that has read the line just written. Pass --no-exec first if you are scripting this and want your own shell back.

After that claude simply works there, on that machine’s own files. Nothing is proxied and no base URL is set: Claude Code reads the token from the environment exactly as Anthropic documents.

Or generate it yourself, on a machine already signed in as that account — same credential, no console involved:

# once, on a machine already signed in as you
claude setup-token

# then once per device — it asks for the token and hides it
bash -c "$(curl -fsSL https://raw.githubusercontent.com/cdcupt/ccfleet/main/laptop/ccfleet-connect.sh)"

After that claude simply works there. The token is Anthropic's own long-lived credential, it lasts a year, and it lives only on the device you put it on. ccfleet-connect --status says whether it still works and --remove undoes it.

One thing a token cannot do

Remote Control. Driving a machine from claude.ai/code or the phone app needs a full-scope login, and Anthropic limits long-lived tokens to inference deliberately — the CLI refuses in as many words. So a node keeps its own sign-in for that, and tokens are for the command line. The two sit side by side; neither replaces the other.

If you prefer a terminal on the node

A terminal is optional, not required. If you want one, connect over SSH and attach to a persistent session so that closing the window does not end your work:

ssh <owner>@<node>
claude            # logging in already attached you to the persistent session

Detach with Ctrl+b then d, or just close the window. The session survives a disconnect. A reboot clears whatever was running inside it, but you do not have to create one again: the node re-creates the session at boot, so your next ssh still lands in it. Remote Control is enabled at boot too, so it comes back on its own.

01What you get

ccfleet manages several personal Claude Code installations without proxying their traffic or holding their logins. Each person gets a small hosted machine (a node) running the unmodified Claude Code CLI, signed in with their own subscription through Anthropic's normal login flow. A tiny agent on each node reports public facts to one fleet server, which draws a dashboard and sends alerts. That is the whole system.

Included

  • Node install: one command takes a blank server to ready-for-sign-in, hardened, with the agent reporting. The older bootstrap and owner-setup scripts remain for machines you manage by hand.
  • Node upkeep: staged upgrades and backups that exclude credentials.
  • Agent: one Python file, standard library only, systemd timer every five minutes.
  • Fleet server: dashboard, JSON API, alert rules, Telegram, node token management.

Deliberately absent

  • No relay or proxy for model traffic.
  • No storage of anyone's credentials; the optional gateway forwards an owner's own requests unchanged and keeps nothing.
  • No header or request rewriting, no fingerprint games.
  • No account pools, share links, seats or automatic failover between accounts.

02Before you start

You needDetails
One Claude subscription per ownerPro or Max. Each owner signs in themselves. Nobody shares an account.
One small VPS per ownerDebian 12, or Ubuntu 22.04 or 24.04. 1 vCPU, 1–2 GB RAM, 20 GB disk, in a region Anthropic supports. About $5–12 per month. The installer is verified end to end on a blank Debian 12.
One box for the fleet serverAnything that runs Docker or Python 3.9+. It can be one of your existing servers. It must sit behind TLS.
SSH keysEach owner has an SSH key pair; nodes accept keys only.
OptionalA Telegram bot for alerts, an rclone remote for off-node backups, a domain for the dashboard.

Read this once

ccfleet keeps you inside the arrangements Anthropic documents: the unmodified Claude Code binary, signed in by its owner, hosted or not. It cannot change where you are. Anthropic's supported-regions list does not include mainland China, Hong Kong or Macau, and a node abroad does not alter that. The compliance notes in the repo quote the exact passages.

03Fleet server

The server is a single process: ccfleetd serve. It listens on loopback, stores everything in one SQLite file, and needs one secret, the admin token. Docker is the quickest path; a plain systemd unit is provided too.

1

Get the code and set the admin token

git clone https://github.com/cdcupt/ccfleet.git
cd ccfleet
cp deploy/ccfleetd.env.example deploy/ccfleetd.env
chmod 600 deploy/ccfleetd.env
openssl rand -hex 32        # paste as CCFLEET_ADMIN_TOKEN in deploy/ccfleetd.env

Set CCFLEET_PUBLIC_URL to the address you will put in front of it, so alerts can link to the dashboard.

2

Start it

# Docker
docker compose -f deploy/docker-compose.yml up -d --build
curl -s http://127.0.0.1:8110/healthz      # {"ok": true}

# or plain Python
pip install git+https://github.com/cdcupt/ccfleet
set -a; . deploy/ccfleetd.env; set +a
ccfleetd serve

For a permanent plain install, deploy/ccfleetd.service runs it as an unprivileged user under systemd; its header comment lists the four commands to set that up.

3

Put TLS in front

# deploy/Caddyfile.example
fleet.example.com {
    reverse_proxy 127.0.0.1:8110
}

Open /admin at that address in a browser. User name admin, password the admin token. The bare address is the product's front page, the same for everybody: what ccfleet is and how to start. Once you have signed in there with Google as an operator, it offers you the console too. You will see an empty fleet with the hint to add a node. That token is the operator's way in and always works; named logins for owners come later, in section 06.

No public endpoint?

You can skip the hostname, the DNS record and the certificate entirely. A node can reach the server through an SSH tunnel instead: a user service forwards a loopback port on the node to this server's loopback port, and the agent posts to its own 127.0.0.1 with SSH providing the encryption. ccfleetd's HTTP endpoint stays private, though the server does still need a reachable SSH port, which is the one surface this design depends on. See docs/tunnel.md in the repo.

4

Register each owner's node

Do this from the console once it is up: add the node, and the page that follows gives you an install command with the server URL, node id and token already in it. Append the owner's --ssh-key before you run it, or the installer skips SSH, firewall and fail2ban hardening rather than risk locking everyone out. Section 04 has the detail.

The token is shown once. Send it to the owner over a private channel, or run the install yourself. Lost it? ccfleetd node rotate-token node-a mints a new one and revokes the old one.

If that owner should be able to check their own node's health, give them a console login as well. Without one they have a node and no way to see whether it is alive:

docker compose -f deploy/docker-compose.yml exec ccfleetd \
  ccfleetd user add alice --owner alice

The password is generated and printed once. See section 06 for what that login can and cannot do.

5

Optional: Telegram alerts

Create a bot with @BotFather, send it one message, read your chat id from @userinfobot, then set CCFLEET_TELEGRAM_BOT_TOKEN and CCFLEET_TELEGRAM_CHAT_ID in the env file and restart. Test with:

docker compose -f deploy/docker-compose.yml exec ccfleetd ccfleetd alert-test

04A node per owner

One command, then one sign-in. The console prints a ready-made install line when you add the node; you run it once on a blank server as root and it takes the machine all the way to the sign-in. It cannot do the sign-in itself, because a subscription login has to complete through Anthropic's own flow, so the owner does that part and nobody else can.

1

Add the node and copy the command

Open the console, fill in the node id and the owner, and submit. The page that follows shows the token once, and an install command with the server URL, node id, token and owner already filled in. Copy it.

The copied command is missing one thing on purpose

The console cannot know the owner's public key, so the command it prints has no --ssh-key. Run it as-is and step 2 will skip SSH, firewall and fail2ban hardening altogether, on purpose, rather than disable password logins on a machine with no key on it and lock everyone out. Add the flag before you run it, or add a key and re-run afterwards.

If you prefer the terminal, the CLI does the same thing and prints the same three identity lines:

docker compose -f deploy/docker-compose.yml exec ccfleetd \
  ccfleetd node add node-a --owner alice --region us-west --rc-expected
  • --rc-expected makes the dashboard alert when the owner's Remote Control service is not running. Leave it out for owners who only use SSH.
  • --pinned-version 2.1.92 can be given now or set later with ccfleetd node pin.
  • Lost the token? ccfleetd node rotate-token node-a mints a new one and revokes the old one.
2

Run it on the blank server, as root

curl -fsSL https://raw.githubusercontent.com/cdcupt/ccfleet/main/node/install.sh \
  | sudo bash -s -- \
      --server https://fleet.example.com \
      --node node-a \
      --token <the 64-character token> \
      --owner alice \
      --ssh-key "ssh-ed25519 AAAA... alice"

It installs packages, creates the owner with a lingering session so their timers survive logout, hardens SSH and the firewall, installs Claude Code, pre-answers the two setup prompts that are not about anyone's account, installs the agent and its units, starts the work session and the timers, and posts a first heartbeat. It prints each step and refuses to call the machine ready if a service did not come up.

  • --ssh-key takes the owner's public key. Without it, SSH hardening is skipped on purpose rather than risk locking everyone out, and you must add a key yourself.
  • --skip-harden leaves the firewall and sshd alone. Use it on a box already carrying other services.
  • --no-remote-control sets up everything else and leaves Remote Control off.

Rerunning it is safe

Every step checks before it acts, so a second run repairs a half-finished install rather than duplicating it. If a service fails to start, the script exits non-zero and names the unit instead of reporting success.

3

The owner signs in

From the console, with no SSH at all. Open the dashboard, find your node under Sign in, and press it. The node starts Claude Code's own login, and within a few seconds the card shows the verification link: open it, approve, and paste the code back into the box on the same card. The card confirms when the node reports the sign-in worked.

What passes through the server, and what does not

Only the verification URL and the code you paste, and both are discarded the moment the sign-in finishes. The credential itself is written by Claude Code into your own home directory on your own node and never reaches the server — the same guarantee as signing in over SSH, without needing SSH.

The terminal route still works, and is the one to use before a node can reach the server:

ssh alice@<node>     # you land straight in the persistent work session
claude

Choose the claude.ai login. Over SSH the browser cannot call back into the node, so Claude Code shows a URL: open it on your laptop, approve, copy the code the page shows, paste it into the terminal. Either way, check afterwards:

/status

The Login row must show your account. There must be no Anthropic base URL line and no Auth token or API key line. If there is, an environment variable is set that should not be; unset it and restart claude.

Where the login lives

On Linux, Claude Code keeps it in ~/.claude/.credentials.json with mode 0600 and refreshes it by itself. The agent asks claude auth status whether the login actually works — the CLI's own answer, rather than an inference from a file existing — and keeps only whether you are signed in, the method, the plan and the expiry. That command also returns your email address and organisation; none of it is copied, and tests on both the agent and the server assert so.

4

The owner turns on Remote Control, once

systemctl --user start claude-remote-control.service

After this, claude.ai/code and the Claude phone app can drive this node with nothing installed on the machine you are sitting at. tmux -L ccfleet-rc attach -t remote-control shows the URL and QR code.

Why the installer does not do this for you

Remote Control needs an authenticated session, and there is none until the sign-in above. The installer therefore enables the service, so it returns by itself after a reboot, but does not start it. It cannot usefully retry either: the unit runs Claude inside a detached tmux session, so systemd sees the launch succeed the moment tmux detaches and never learns that the session failed to authenticate. One command by the owner is honest; an automatic retry would not work.

5

Optional: off-node backups

The nightly backup already runs locally (~/backups/ccfleet, last 14 kept, credentials excluded). To copy archives elsewhere, install rclone, configure a remote, and create ~/.config/ccfleet/backup.env:

CCFLEET_BACKUP_REMOTE=r2:my-bucket/ccfleet/node-a
CCFLEET_BACKUP_EXTRA=/home/alice/projects

The long way round is still there, but it is not equivalent

If you would rather not paste a token into a command, the console also prints the three agent.env lines on their own. Run node/bootstrap.sh as root, then node/setup-owner.sh as the owner, and place those lines in ~/.config/ccfleet/agent.env afterwards. That order is not optional: the owner's account and home directory do not exist until the first script has run.

Those two scripts cover the packages, the owner account, sudo, the firewall, lingering, the helper binaries and the agent, backup and work-session timers. They do not do the rest, and you are taking it on yourself:

  • No fail2ban. bootstrap.sh does not install or configure it, so the node has no SSH brute-force protection until you add it.
  • Claude Code's two setup prompts are not pre-answered, so the owner meets them interactively.
  • agent.env is created, but from a template. The URL, node id and token in it are placeholders you replace by hand.
  • Remote Control is not enabled by the script. Its closing message tells the owner to do it, so until they do it will not return after a reboot.
  • Both scripts run under set -euo pipefail, so a unit that fails to start does abort them. Neither re-checks the units afterwards nor sends a first heartbeat, so a service that starts and then dies goes unnoticed until the dashboard misses it.

Section 04 above is the supported path. Reach for this one only on a machine you are managing by hand, and close those gaps deliberately.

05One account per computer

A computer uses one Claude account, connected with that account's token through ccfleet-connect; several accounts means several slots, one for each.

The same account can be on as many of your own computers as you like, each with the same token. What a computer never does is keep a second account on the side to switch to: connecting again with another account's token replaces the one it had, and says so. The --add, --use and --list of an earlier version are refused. On a computer that saved several tokens under names, the first run keeps the one in use and removes the rest, telling you how many went so you can revoke them in your Claude account. Section 00 has the setup.

06Daily use

Who can sign in

The console takes two kinds of credential.

CredentialSeesCan manage nodes
The admin token
user name admin, or any name at all		the whole fleetyes
ccfleetd user add NAME --role adminthe whole fleetyes
ccfleetd user add NAME --owner OWNERonly that owner's nodesno — except signing their own node in

An owner login can do exactly one thing: start a sign-in on a node they already own. That is the whole point — needing the operator to sign you in would only move the bottleneck. Everything else is refused, and the missing forms are only the cosmetic half: every write route checks the role and the node's owner, so a hand-built request is answered 403 rather than 401. Their credentials were fine; the action was not theirs. An owner is given a CSRF token so their own form works, and the tests state plainly that a CSRF token is not authorisation: disable, rc-off, rotate-token and remove are all still refused to an owner holding a valid one.

Manage them with ccfleetd user list, ccfleetd user passwd NAME and ccfleetd user remove NAME. Passwords are stored as salted PBKDF2 hashes and cannot be recovered, only reset.

What this is not, yet

There are no sessions, so the browser holds the credentials for the realm until it is closed, and there is no self-service password change: resetting one is the operator's job.

Four tiles sit above the table — healthy, warning, critical, disabled — so the first question ("is anything wrong?") is answered before you read a row. A tile at zero stays grey rather than competing with the one that is not. A shared machine's row is its slot. Root on a shared machine runs no Claude Code and is signed in to nothing, so the row shows the slot's version, sign-in, Remote Control and usage, and goes by the slot's name: the machine's hostname, which is what claude.ai shows. While somebody holds the slot, that is their name, said alone: not the machine's id nor its owner, here, in the Slots card or on the holder's own page; ccfleetd slot list says which machine a name is on. Once the slot is given back, the machine answers to its pool name again. Login says no slot yet on a machine with none declared, and 2 slots, see Slots on one from before one slot per machine, where no single slot can speak for it. Remote Control is the slot's to run, so a machine is never judged on it and its row has no switch for that alert. The sign-in and device-token cards list owners' nodes only: a slot is signed in, and gets its device tokens, on its holder's page, and the server refuses a console sign-in on a shared machine.

Usage and quota

Under the fleet table, one row per node, answering two different questions.

How much is left. Two bars: the five-hour session window and the week. This is the number an owner actually asks for, and it exists in exactly one place — /usage, inside a running Claude Code session. So the agent opens one on a slow schedule, roughly every half hour, in a throwaway tmux session pinned to the owner's home directory, reads the two windows off the screen and sends the percentages and reset times up with the heartbeat. Claude Code reporting on itself; there is no usage endpoint behind this. A reading takes about nine seconds, and the console says how old the one it is showing is.

How much was spent. A sparkline of daily tokens and the totals behind it, counted from the transcripts Claude Code writes on the node. Different question, different source: this is what the account consumed, and it says nothing about the window. A node with a single day of history says so rather than drawing a chart of one point.

What each counts. The bars are the whole Claude account's: claude.ai, the Claude app, and Claude Code on any computer, device tokens included. The tokens are only what ran on this node, or in the slot on a shared machine. Somebody who works mostly from their own computer with a device token can see a quarter of the week gone beside a small token count, and both are right; the console and the holder's page each say so under the numbers.

When a window resets. Claude Code prints a reset in the machine's own clock, and the machines keep theirs on UTC. The server places those words at a moment, and the page shows it in the viewer's own time zone with how long is left beside it: Thu 10:00 AM GMT+2 (in 2d 5h). One small script does that, the only script ccfleet's pages carry, and their Content-Security-Policy allows it by its SHA-256 and nothing else. Without it the page still says how long is left, and words the server cannot place stay as Claude Code printed them.

Conversation content never leaves the node; only counts do. The server whitelists the quota block the way it whitelists everything else a node sends: two named windows, an integer from 0 to 100 or nothing at all, and a short reset string. A node cannot widen that by sending more.

The page refreshes itself every minute. GET /api/nodes and GET /api/alerts return the same data as JSON with the same Basic auth, or with Authorization: Bearer <admin token>, for scripts and status pages. They are scoped the same way the page is, so an owner account gets only its own nodes.

Working on a node

  • Terminal: ssh alice@node or mosh alice@node. You land in the persistent session automatically, with no tmux command to remember. mosh survives laptop sleep and roaming.
  • VS Code: Remote-SSH to the node; the Claude Code extension runs there with the node's login.
  • Phone or any browser: claude.ai/code, pick the node's session (it carries the node's hostname).
  • Usage windows: type /usage inside a session on the node. Windows are per account; a second account is a second window, not a bigger one.

07Operations

Staged upgrades

Auto-update is off on nodes on purpose, and the pin is authoritative: a node that finds itself on a different version installs the pinned one and reports the result. So an upgrade is driven from the server, one node at a time.

# on the server — pin one node first
ccfleetd node pin node-a 2.1.92
# confirm the row shows it with no failure, work a day, then pin the rest
ccfleetd node pin node-b 2.1.92
# or track a channel, latest or stable; a channel pin never reports drift
ccfleetd node pin node-a latest

A channel follows Anthropic's own release numbers, which the server reads about hourly from the files the official installer reads, and sends with every reply. A node installs a new release at its next quiet moment, never while somebody is signing in. Without a number from the server it resolves the channel itself, once a day.

Upgrading on the node no longer sticks. While a pin is set, the next heartbeat installs the pinned version over whatever ccfleet-upgrade-claude just put there. Change the pin instead, or run that node's agent with --no-reconcile to work outside it.

Give someone the CLI on their own machines

The account owner does this themselves; you cannot do it for them, and should not be handed the result:

# the OWNER runs this, on a machine signed in as their account
claude setup-token

# then on each of their devices
bash -c "$(curl -fsSL https://raw.githubusercontent.com/cdcupt/ccfleet/main/laptop/ccfleet-connect.sh)"

Do not ask them to send you the token. It is their account's credential for a year; the point of this route is that it never passes through anyone else, including you.

One year, inference scope, and it never touches this server. There is nothing to revoke here because nothing is stored here; revocation is in their Claude account.

Rotate a node token

ccfleetd node rotate-token node-a
# then update the node's agent.env

The old token stops working immediately.

Rebuild a node

  1. New VPS, then the one install command from the console (rotate the token first, so the command carries a valid one).
  2. Restore the latest claude-state-*.tar.gz with tar -xzf claude-state-<stamp>.tar.gz -C / (archive paths are relative to /). It contains settings, projects and history, never credentials.
  3. Owner runs claude and /login.

Remove an owner

ccfleetd node disable node-b   # keep history
ccfleetd node remove node-b    # delete it all

The owner runs /logout on the node before it is destroyed.

The repo's docs/runbooks.md has one short procedure per alert, plus the quarterly reminder to re-read Anthropic's terms and gateway pages.

08Optional pass-through gateway

For an owner who cannot work on a remote filesystem, Anthropic's gateway docs describe a second permitted arrangement: Claude Code runs and logs in on the laptop, only ANTHROPIC_BASE_URL points at a gateway, and the saved claude.ai login stays the active credential. gateway/Caddyfile.example implements it: it requires a private header, drops that header, passes the body and Anthropic's required headers through unchanged with streaming on, and stores nothing. Like any reverse proxy it does set Host and add X-Forwarded-*; what it never does is substitute a credential or alter who the client says it is.

# laptop
export ANTHROPIC_BASE_URL=https://gw-a.example.com
export ANTHROPIC_CUSTOM_HEADERS="X-Gw-Key: <secret shared with the gateway>"
claude
/status      # base URL shows the gateway; Login row still shows your account

Two cautions

Never authenticate the gateway with ANTHROPIC_AUTH_TOKEN: that variable replaces the subscription as the credential. The Caddyfile has now been exercised against a live session: a real session completed through it, and stopping the gateway made the same command fail while restarting it made it work again, so it was genuinely in the path. That test ran over a loopback port through an SSH tunnel, so TLS termination and a public hostname are still unexercised; run a long streamed session over the real hostname before depending on it. One gateway, one owner, one account.

11Shared machines

A shared machine carries one slot: one Linux user for one person, with its own Claude Code signed in to that person's own Claude account, so no credential is ever shared. One machine is one slot because claude.ai/code shows a machine by its hostname: claimed, the slot is named after its holder (alice-1) and the machine takes that name. People sign in to the product with Google, you set how many slots each may hold, and they do everything else themselves at /account.

One Claude account, one slot: a slot is signed in to one account at a time, and somebody who wants two accounts at once holds two slots. Its holder can move it to another Claude account of theirs with Change account, at most once a week, and keeps its files. Its account can be used from wherever its holder likes: claude.ai/code and the Claude app on any device, or a device token on each of their own computers.

Selling a slot

  1. The person signs in once at /account. That creates the account you switch on; an address that has never signed in cannot be given anything.
  2. They pay you, however you arrange it.
  3. You record the payment and set their allowance in the console's Accounts card. The payment's date comes filled in with one more month: from the day after what they have already paid for, or from today when that has passed or nothing is paid yet, so a first payment on 24 September suggests 23 October. That is all you do. The same card says, beside how many slots each person holds, the Claude plans on them: holds 2 (Max 20x, Pro).
  4. They claim a slot, sign in to Claude with their own account, and use it from claude.ai/code or the Claude app.

The price of a slot for a month is yours to set, in the console's Price card or with ccfleetd price set 20 USD, and the public pages show it. It is shown, never charged: people still pay you directly, the allowance is still the only thing that lets somebody claim a slot, and the payments you record stay a record. With no price set, the pages say price and payment are agreed with you.

Send them the bare address (/docs is the same page). It says what ccfleet is, what they must bring (their own Pro, Max, Team or Enterprise plan; API keys do not work) and how to start, and links /docs/guide, /docs/how-it-works, /docs/terms and /privacy. It is the same page for everybody; only its buttons follow whoever is looking: Sign in with Google for a visitor, Your slots once signed in, and Console as well for an operator. Set CCFLEET_CONTACT_EMAIL to publish an address on them.

Every page shares one top bar. Signed in, a round avatar at the top right opens a menu with the person's address, Your slots with how many they hold, Console for operators, and Sign out; signed out, the same spot is Sign in. The mark at the top left goes to the front page from every page, the console's included, and the console's back to the fleet links go to the console.

Sizing

Measured on a real slot: signed in with Remote Control, about 420 MiB idle and 665 MiB in use, plus 225 MB of disk. The OS and the agent take about 400 MiB, so a 2 GiB machine carries its one slot with room to spare. Under 4 GiB, add a 2 GiB swap file as a cushion.

Adding a machine

A KVM VPS running Debian or Ubuntu; LXC and OpenVZ cannot run per-user systemd reliably. docs/runbooks.md has every step and check; in short:

# your key first — and prove key login works before anything turns passwords off
sudo ./bootstrap.sh you "ssh-ed25519 AAAA… you"
# on the server
ccfleetd node add pool-1 --owner you --region us-west
ccfleetd node pin pool-1 latest
ccfleetd slot add pool-1 --machine pool-1 --unix-user slot01
# on the machine, as root: its name, its clock on UTC, then the agent
hostnamectl set-hostname pool-1 && timedatectl set-timezone Etc/UTC
curl -fsSL https://raw.githubusercontent.com/cdcupt/ccfleet/main/node/machine-setup.sh \
  | sudo bash -s -- --server https://fleet.example.com --node pool-1 --token <64-hex>
# back on the server: its slot free, and "on machine: no"
ccfleetd slot list --machine pool-1

Set the machine's hostname to its id first: it is the name the claude.ai machine picker shows until somebody claims its slot. Put its clock on UTC as well: Claude Code can tell Anthropic the machine's time zone, and UTC says nothing about where the slot's holder is, while every page shows times in the viewer's own zone. Machines are named by role, <you>-N for your own and pool-N for the ones offered to customers, and a free slot by its machine.

  • Names follow holders. A claimed slot is named <handle>-<n>: the part of the address before the @, unless you pick a handle with ccfleetd account handle. The machine takes that name as its hostname before the slot is set up, and answers to its own id again once the wipe that frees the slot completes.
  • Renaming a running fleet: ccfleetd node rename and ccfleetd slot rename, held slots included. The runbook Rename a machine in docs/runbooks.md has the order.
  • A machine kept for one account: ccfleetd node reserve <machine> <email> hands its free slot to that account and nobody else; --none opens it again. Customers never see a reservation.
  • Somebody's own node counts as one of their slots with ccfleetd node hold <node> <email>: a record only, never handed out or wiped.

Keeping it current

  • Claude Code in slots follows the machine's pin: latest or stable tracks that Anthropic channel, and an exact version holds the whole machine back. The machine agent installs a new release at a quiet moment, never during a sign-in, and never interrupts a running session; Remote Control moves over once no session is open.
  • Holders choose for their own slot. The Claude Code row on their card shows the version and, once a newer one is out, Update to that number: it switches the slot to latest and installs now. Back to Stable goes back. An exact pin on the machine overrides both, and the row says held by the operator. On somebody's own node the buttons set that node's pin, which is theirs and never a hold.
  • The agents: after a release that changes them, update one node first, then the rest. Owner nodes re-fetch the agent; machines re-run machine-setup.sh pointed at that commit with CCFLEET_REPO_RAW.
  • The OS installs security updates daily; a machine that needs a reboot says so in the console.

What a slot starts with

Claude Code on a new slot starts on Opus at max effort, and sends Anthropic nothing optional that a slot can do without. Setting a slot up writes these keys into its ~/.claude/settings.json, and only keys the holder has not set, so setting it up again never takes a choice back:

{ "model": "opus",
  "env": { "CLAUDE_CODE_EFFORT_LEVEL": "max",
           "DISABLE_ERROR_REPORTING": "1",
           "DISABLE_BUG_COMMAND": "1",
           "CLAUDE_CODE_DISABLE_FEEDBACK_SURVEY": "1" } }
  • Max goes in env. The settings file's own effortLevel stops at xhigh and drops max without a word. The variable pins every session at max, so /effort cannot lower it; a holder who wants less edits that line, and /docs/guide tells them how. /model still changes the model for a session.
  • opus is the newest Opus that the installed Claude Code knows. Opus 5.5 needs Claude Code 2.1.280 or later. On 2026-09-24 only latest had that, and a slot on stable got Opus 5, which is why machines are pinned to latest.
  • It costs the holder. Max effort uses their plan's limits fastest, and the guide says so.
  • Error reports, bug reports and feedback surveys are off, by Claude Code's own documented switches. What still goes is what Claude needs to answer, and its usage telemetry, which Remote Control needs (below).
  • A slot is the machine, not the person. Nothing rewrites what Claude Code says about where it runs: no faked location, time zone or device. Anthropic sees the machine, with its own address and its UTC clock, and the holder's own Claude account. The holder's browser or Claude app, driving the slot, talks to Anthropic as it always would.

Never switch telemetry off on a slot

Remote Control needs the feature-flag evaluation that DISABLE_TELEMETRY turns off, and CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC includes it. With either one set, Remote Control refuses to start: Remote Control requires feature-flag evaluation, which is disabled because DISABLE_TELEMETRY is set. Set on live slots once, it stopped Remote Control on every one of them until it came out; a test now keeps both out of what a slot starts with.

The console's Slots card

One line on top gives Anthropic's release numbers, for example Claude Code releases: Latest 2.1.281 · Stable 2.1.273 · checked 5m ago. Under it, one row per machine, and the machine's slot is the row:

HolderTheir address and, under it, the Claude plan of the account signed in on the slot (Pro, Max 5x, Max 20x…), or free
StateThe words the holder's own page uses: In use, Ready to sign in, Setting up, Being wiped, or Free. An own machine reads In use or Not signed in

Manage ▾ on each row holds every action, so nothing that wipes sits on the row itself:

  • Take back: the slot's name, as the row shows it, has to be typed to confirm. A slot given back and claimed by somebody else since the page was drawn has another name by then, so the old one is refused.
  • Remove, for a free slot.
  • Keep for somebody, or Clear reservation on a kept machine.
  • Advanced, only where it can do something: declaring the slot of a machine that has none yet, or the capacity of a machine from before one slot per machine.

An own machine has no forms; the one command that stops counting it is inside its Manage. At 960 px and narrower, phones included, the rows become cards.

For a week after a holder moves their slot to another Claude account, a line under its row says changed Claude account <age> ago. It never says which account; that is the holder's to see.

One account per slot, enforced

The product keeps the rule without relying on anybody to remember it:

  • A slot binds to its account. The first Claude account signed in on a slot is the one it keeps, until its holder moves it with Change account. The binding lives in the slot's own state, so it goes with the slot's wipe.
  • Sign in again only takes that account. It signs in to one side, in a scratch directory, and keeps the result only if it is the same account. Any other account is thrown away with this slot stays with its own Claude account; to move it to another, use Change account, and the sign-in the slot already had is left as it was.
  • Change account moves it, at most once a week. It is offered on a shared machine's slot in use, never on somebody's own node. The new account signs in to the scratch directory while the old one keeps working, and only a finished sign-in is moved in, in order: the account block of ~/.claude.json (every other key stays), then the credential, then the binding. A step that fails puts back the ones before it, so a change that fails leaves the slot as it was; should putting back fail too, the holder's page says it stopped halfway, and changing account again finishes it. There is only ever one credential on the slot, so it never holds two accounts. Remote Control then restarts on the new account, which ends any session open in it, and the slot shows in claude.ai/code under that account instead. Signing in with the account the slot already has is not a change; the week starts only when the account really moved. The files stay throughout.
  • One account is in one place. Every node and slot reports a fingerprint of its account: the first 16 hex characters of a SHA-256 of Claude's account id, never the id itself, and never an owner node's address. One account live in two places raises account_elsewhere on both; a held slot signed in to another account than its own raises account_changed. The holder's card says so too, without naming the other place.

What it cannot stop

A slot is its holder's own Linux account, and they can change its files: sign in there by hand, or put another account's credential in place. ccfleet notices with account_changed — a hand sign-in at the next report, a swapped credential once Claude Code next refreshes its profile — but cannot prevent it. That is detection, not prevention. The terms say one account per slot, and taking the slot back is yours to decide.

Key login before hardening

Some provider images ship with PubkeyAuthentication no. Turning passwords off on such a machine leaves nothing but the provider's console. bootstrap.sh and install.sh refuse to turn passwords off unless key login is in force, but prove it yourself before you close the session you are in.
