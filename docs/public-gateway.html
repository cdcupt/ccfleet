Local Claude Code through our public HTTPS gateway

Our own-domain API

The gateway gives users one HTTPS address and a revocable endpoint key. Original Claude Code still runs on their computer. It sends model requests to our domain on Bandwagon Host (BWH), where CC Fleet routes them to the user's selected slots. Files, tools, plugins and native conversation history remain local.

This changes the model-request route. A configured gateway launch does not start a local HTTP server or use laptop-side SSH. BWH still uses a restricted SSH service connection to the chosen slot. That slot opens HTTPS to Anthropic using its own Claude credential. Anthropic runs the model.

The original local bridge remains available with ccfleet local --transport bridge. It is useful when someone deliberately wants laptop-to-slot SSH through the byte broker. A configured gateway that becomes unavailable reports an error; it does not silently switch to the old bridge or another user's account.

Start with the CLI

The direct gateway workflow is part of client release 0.2.5. Install or update through the normal setup command:

curl -fsSL https://raw.githubusercontent.com/cdcupt/ccfleet/main/laptop/install.sh | bash -s -- --setup

On a new computer, setup asks for a fresh code from Connect this computer on Your slots. When gateway access is available, it creates a separate endpoint key for that paired slot and saves the key privately. An existing pairing, Claude installation, project files and native history are preserved. Previously paired computers can enroll explicitly:

ccfleet gateway setup
ccfleet local

Setup does not print the endpoint secret. The saved gateway configuration is private to the local user. A readiness check does not upload project files or start a model request. If setup identifies an old live-folder grant, its existing explicit cleanup flow still applies; ending those old sessions is a separate action.

ccfleet gateway status
ccfleet local --check
ccfleet gateway remove

remove revokes the saved endpoint key before removing its local configuration. It does not release slots, erase history, or revoke the slot's Claude credential. Use ccfleet gateway setup --replace to deliberately replace a revoked or existing key.

Choose your accounts

Imagine you hold two slots: work-primary and work-backup. Each slot remains signed into one Claude account. An endpoint selects slots; it does not copy or combine their credentials.

Your goalSelectionBehavior
Use only one specific accountSelect only work-primaryRequests use that slot. Its failure cannot broaden the endpoint to other slots.
Keep each conversation on one account, with a backupSelect work-primary first, work-backup second; choose stickyThe first successful slot is remembered for that conversation. A safe failure can move it to the backup.
Prefer the first available account for every requestSelect both in that order; choose priorityEach request starts with the highest-priority eligible slot, subject to short failure cooldowns.
ccfleet gateway setup --slots work-primary work-backup --routing sticky
ccfleet local

# Prefer the first eligible account for each request.
ccfleet gateway setup --slots work-primary work-backup --routing priority

# Pin one selected slot for this launch; do not fail over to another slot.
ccfleet local --slot work-primary

On Your slots → API endpoints, enter 1 for the first choice, 2 for the backup, and leave excluded slots blank. Give each selected slot a different priority. Choose Keep each conversation on one account or Prefer the first available account for each request. You can create separate keys for different applications, update their routing, and revoke them independently.

Only the current user's own held hosted slots are selectable. Administrator status does not widen that pool. A slot still being provisioned or signed in may be selected, but cannot receive model requests until ready. Released slots are removed from eligibility immediately. Reclaiming the same slot does not silently reactivate an old selection: update the endpoint deliberately.

Sticky routing needs a usable conversation identifier. Native Claude Code identifiers are recognized; compatible clients can send X-CCFleet-Session. Without one, requests use the selected priority order. Affinity is bounded runtime memory, retained for up to 24 hours after success. A service restart, configuration generation change, account transition, or unavailable slot may establish a new assignment. Conversation history stays in the local client.

One request, step by step

  1. Claude Code prepares the model request. It includes the prompt, relevant context, model name and tool descriptions. If a local file or tool result becomes model context, that content travels in the request.
  2. HTTPS delivers it to our domain on BWH. The gateway accepts the separate endpoint key, validates the method, path, request framing and JSON, and checks the selected slots against current ownership and lifecycle. Device, node and administrator credentials do not authenticate model requests.
  3. The gateway chooses an eligible slot. Selection follows the endpoint's single-slot, priority or sticky rules. Known unhealthy login reports and pending sign-in transitions are excluded.
  4. BWH opens the inference-only SSH connection. It pins the configured slot SSH host key. Readiness is checked on this same connection before any model request data is sent. The slot validates its root-managed inference policy and native account binding.
  5. The slot sends a new HTTPS request to Anthropic. Its relay filters selected client identity fields, reads the current native credential, and adds upstream authentication. Native Claude remains the only credential writer and handles renewal.
  6. The response streams back. BWH forwards response chunks to local Claude Code. Local Claude executes requested tools according to local permissions and can send their results in another model request. Disconnecting, exceeding the request deadline, or losing authorization cancels the active transport.

Understand the URL

https://fleet.example.com/v1/messages
PartMeaning
https://Use HTTP protected by TLS encryption.
fleet.example.comOur public server address. The example is a placeholder for the deployment's existing product domain.
/v1/messagesThe Messages API path. It identifies the operation, not a particular model or user account.

A Base URL is the origin, such as https://fleet.example.com. The client adds the supported path. A model request uses POST: send a JSON document to the service. The gateway and slot preserve the supported API path while the receiving server changes along the route.

The public route no longer starts with a temporary address such as http://127.0.0.1:54321. That address belongs to the explicit legacy bridge workflow described in the local bridge reference.

When a backup is safe

Failover is useful when the first selected slot is down, signing in, throttled, or temporarily unable to accept a request. It must not turn an interrupted request into a duplicate model run.

  • Before the model request is sent: an unavailable slot or failed readiness check can move to the next selected slot.
  • After sending: only an explicit response marked safe to retry by the slot, with an eligible rejection status, can trigger a backup. The current status set includes authentication, maintenance, rate-limit and temporary-unavailability responses; the status number alone is insufficient.
  • An uncertain transport failure is not replayed: once writing the model request begins, losing the connection does not prove that the upstream request was rejected. The gateway returns an error instead of guessing.
  • After public response headers are sent: no backup or replay occurs, even if zero response-body bytes have arrived. A broken stream ends.

A pinned launch or a one-slot endpoint cannot try an unselected account. Failure cooldowns are short and scoped to the endpoint, slot and model. Routing does not create capacity: each selected Claude account still has its own provider limits. A user can deliberately send a new request after an error; that decision is separate from automatic failover.

What each server can read

BWH can read model requests and responses in the direct API workflow. TLS ends at the HTTPS service on BWH, which parses the request and chooses a slot. The BWH-to-slot SSH connection encrypts that next hop, but does not hide contents from BWH. The slot and Anthropic also see the model request. Administrators controlling those endpoints can access its contents.

The original bridge has a different boundary: its inner laptop-to-slot SSH encryption passes through the BWH byte broker, so that forwarding service carries ciphertext. Keep --transport bridge when that particular boundary matters. Both routes can expose file contents through ordinary model context; keeping the filesystem local does not mean every file's text remains local.

For an own-domain deployment, the default design uses a DNS-only record pointing to BWH and TLS on BWH. Cloudflare can manage the domain's DNS without proxying HTTP traffic. If Cloudflare's HTTP proxy is enabled, client TLS ends at Cloudflare before its separate origin connection, adding Cloudflare as a party able to process the request. See Cloudflare's proxy-status explanation and edge/origin TLS concepts.

Selected identity headers and structured metadata are filtered; this does not remove identifying details embedded in prompts, paths, code or tool results. Gateway keys are separate from Claude credentials. Model bodies are not part of the key database or safe status output. Native history stays local, while slot relay observations remain limited to their existing numeric aggregates. Avoid adding request-body or authorization-header logging when operating a reverse proxy.

The final Anthropic connection still comes from the slot's Python relay. This change does not prove an identical native Claude Code TLS fingerprint, and does not move Anthropic's observed egress address to BWH.

Slot's Claude credentialThat slot's native credential storeUpstream account authentication. Native Claude writes and renews it; it is not returned to the client or BWH.

Changing slot selection or routing increments the endpoint generation and invalidates its previous request authorization and affinity. Revoking a key invalidates requests using that key. Release, account transition, node disablement and connection changes invalidate the relevant slot generation. These checks continue during active streams.

The service public key is advertised only for a current eligible rental selected by an active endpoint key. Nodes reconcile and remove obsolete service grants. Node reconciliation is asynchronous; fleet-side authorization denies revoked requests immediately, while the slot's account and root-managed policy provide their own final check. Existing ordinary device pairings retain their original forced command.

Transport limits

The default public gateway accepts at most 16 MiB per model request. This is a bound on the serialized HTTP request body, not a project-folder size limit, file-count limit, Git-ignore rule, or permission to upload the whole project. Claude's context window and account usage limits remain separate.

DefaultPurpose
16 active requests globallyBound concurrent processing and slot transports.
8 active requests per endpoint keyKeep one client from occupying the whole gateway.
32 MiB raw-body reservation budgetBound total admitted request-body sizes. JSON decoding and response processing need additional memory.
128 accepted connectionsBound connection/thread admission. This is not 128 simultaneous model requests.
10-second header deadline; 900-second request deadlineBound slow header clients and request lifetime.

Oversized requests receive 413. Busy admission or no usable selected slot receives 503. The public API requires one canonical content length, JSON and a supported path; it refuses request compression, transfer encoding and ambiguous authentication or routing headers. The raw-body budget is not a claim that the service's total process memory stays below 32 MiB.

API reference

Use the deployment's existing HTTPS product origin as the Base URL. Authenticate each request with exactly one Authorization: Bearer YOUR_ENDPOINT_KEY header or one x-api-key: YOUR_ENDPOINT_KEY header. Do not send both. The example key is a placeholder.

The endpoint key authenticates you to CC Fleet. It is not an Anthropic paid API key and does not replace your own Claude plan. Native Claude Code supplies its protocol version and beta headers. A compatible client must also provide the headers required by the current native OAuth slot path; gateway authentication alone is not a complete Anthropic request.

Content-Type: application/json
anthropic-version: 2023-06-01
anthropic-beta: oauth-2025-04-20

These version and OAuth beta values were verified for the current relay path. The version selects API behavior, not a Claude model; the beta header identifies the OAuth protocol feature. They travel alongside the separate endpoint-key header. A headerless manual request can be rejected even when the key and routing are valid. Acceptance of this tested path does not establish official provider approval or native Claude Code TLS fingerprint parity.

For compatible clients, X-CCFleet-Session supplies a conversation identifier for sticky routing. X-CCFleet-Slot pins a request to a slot already selected for the endpoint; it cannot widen that selection and disables fallback for the pinned request. These routing fields are consumed by CC Fleet, rather than forwarded as provider identity.

The Messages endpoint is a bounded compatible interface, not a promise to proxy arbitrary URLs, methods, Anthropic services or third-party providers. The gateway requires POST on its fixed model paths and never accepts a caller-controlled slot network address.

Operator setup

Keep the existing product domain and TLS reverse proxy on BWH. The model routes join the product service; no separate Cloudflare Worker or public per-slot HTTPS endpoint is required. Keep the application listener on loopback behind TLS, and use DNS-only records for the direct BWH design.

Configure the gateway using deploy/ccfleetd.env.example. The private service key must be a dedicated inference identity, readable only by the gateway service user. Mount the private key at the configured absolute path in the actual service environment; keep it out of the image, repository, API responses and heartbeat payloads. Configure its matching public key separately.

CCFLEET_PUBLIC_URL=https://fleet.example.com
CCFLEET_GATEWAY_ENABLED=true
CCFLEET_GATEWAY_SSH_KEY_PATH=/run/ccfleet-secrets/gateway_ed25519
CCFLEET_GATEWAY_SSH_PUBLIC_KEY=ssh-ed25519 YOUR_MATCHING_PUBLIC_KEY

These are configuration placeholders, not usable credentials. gateway_ready means configuration is available: the product service is enabled and has a service-key path, public key and public URL. Startup validates the configuration format; it does not prove that the mounted private key is usable or that a slot is reachable. Broker-only deployments do not expose the model API.

The authenticated read-only status check separately probes eligible slots through bounded SSH connections, with briefly cached observations. It checks transport, slot policy and native account readiness without a model POST. A successful check is useful evidence that the route is ready; it is not proof that Anthropic will accept the next request.

Each selected node needs the updated machine agent, gateway-capable slot relay and forced entry script. Its managed account must use the verified root-installed /bin/dash login shell, so holder-writable Bash startup files cannot run before the trusted SSH entrypoint. Its sshd slot block must read only root-managed authorized-key files, disable alternate key-command/CA sources, and respect each key's own forced command. A group-wide ForceCommand would override the gateway key's narrower entry and must be removed only after the read-only key audit passes.

Only the gateway's public service key reaches a selected eligible current rental, forced to the inference-only gateway protocol with no PTY or forwarding. The private key remains on BWH. Nodes also need the explicit root-managed inference opt-in and a healthy native account binding. Let public-key intent converge and run read-only readiness checks before user traffic. Preserve ordinary SSH device grants and the explicit legacy bridge; updating a login shell does not rewrite dotfiles or end existing tmux sessions.

Resource settings must account for decoded JSON, active streams, the base service, and native transport processes. The default reservations limit admission; they do not replace measured memory and load checks on BWH. Keep prompts, model output, endpoint secrets and upstream credentials out of diagnostics and support exports.

Verification and rollout

Verification update: 2026-10-11. The gateway implementation at source revision 1494f6b was deployed to the primary/broker services and three managed nodes. The normal public stable channel publishes signed client 0.2.5. CI completed successfully: Python test runs reported 5,337 passes and 5 intentional skips; a separate disposable Linux fixture passed 4 real OpenSSH tests.

  • Live native client: original local Claude Code from the signed 0.2.5 bundle completed a real Haiku request on one explicitly pinned production slot. Synthetic local Read/Write checks verified exact bytes and the response streamed through SSE. Model transport used HTTPS only, with no laptop SSH process or local bridge.
  • Protocol compatibility: a correctly framed request with the version/OAuth beta headers above returned HTTP 200 from /v1/messages/count_tokens. The legacy bridge's read-only readiness check also passed; it made no additional model request.
  • Authorization and routing: disposable-key revocation returned HTTP 401 while the existing device pairing IDs and rental were preserved. Ordered multi-slot routing, sticky affinity, safe failover, uncertain-send refusal and stream cancellation were verified with controlled peers and fault tests.
  • Edge privacy: isolated tests on the exact Caddy 2.11.3 image forced HTTP 502 errors with synthetic authorization, API-key, session and query markers. Fleet-specific runtime-error suppression plus explicit route logger naming protected both normal and uppercase hosts with port suffixes, while the other test tenant's error logging stayed intact. Before the targeted production logging reload, no active upgrade markers were observed; unrelated configuration and the observed statuses of all 18 tenants stayed unchanged.

The live provider exercise covered one pinned slot. Controlled multi-slot tests are not a live multi-account provider pilot, sustained uptime benchmark, or proof of every model and client combination. Read-only readiness, CI and a reply alone do not establish anonymity, zero metadata disclosure, official provider approval, or native TLS fingerprint parity. Production checks used synthetic owned data and disposable endpoint keys rather than existing user prompts, histories or credentials.

Read-only checks such as ccfleet gateway status, ccfleet local --check, and the safe status API make no model request. They can report configuration or slot readiness, but only an explicitly authorized upstream request proves acceptance by Anthropic. Additional models, clients or account pools need their own recorded verification; the proof above covers the stated cases.
