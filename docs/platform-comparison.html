CC Fleet and CC Host: evidence-based comparison

CC Fleet implementation updated 2026-10-11. CC Host entries retain the public documentation review from 2026-09-30 UTC; they are not a fresh competitor audit or an independent runtime, security or performance assessment. Earlier bridge deployment evidence lives in the verification record. The new gateway's live-verification status is recorded separately in the public gateway guide.

There is not enough comparative evidence to call either platform best overall. The reviewed CC Host documentation describes a broader product. CC Fleet focuses on a native local Claude experience, one bound Claude account per slot, and endpoint selection of one or several slots held by the same user.

How to read “win” and “loss”. Our tested controls include own-slot authorization, independently revocable endpoint and device keys, restricted pinned SSH to slots, and deliberately smaller stored analytics. The explicit legacy bridge also retains laptop-to-slot SSH encryption through BWH; the new HTTPS gateway lets BWH read model requests. These controls do not prove that CC Host lacks equivalent protections. Feature breadth, measured usability, privacy boundaries and availability must be scored separately.

These differences support no blanket superiority claim: direct HTTPS makes client setup simpler and gives BWH access to model contents, while optional multi-slot routing provides backups only within a user's explicit selection.

What changed with the public gateway

CC Fleet now offers the same general client setup shape as the documented CC Host endpoint workflow: a remote HTTPS Base URL and an application key. Our implementation is described in the public Messages gateway guide; CC Host's internal transport and TLS implementation remain unverified.

Current gateway:
local original Claude Code
  → HTTPS on our domain / BWH: endpoint authentication and own-slot routing
  → restricted pinned service SSH to the chosen slot
  → HTTPS from that slot to Anthropic

Explicit legacy bridge: ccfleet local --transport bridge
local original Claude Code
  → authenticated local HTTP listener
  → laptop-to-slot SSH inside BWH's WebSocket byte broker
  → HTTPS from the assigned slot to Anthropic

A user holding two slots can select just the first, or select both with an explicit priority. Sticky mode remembers a usable conversation identifier in bounded runtime memory; priority mode starts each request with the first eligible slot, subject to short failure cooldowns. Neither mode can select someone else's slot or combine several credentials inside one slot.

Before model data is sent, a failed readiness check can move to the next selected slot. After sending, only an explicit rejection marked safe to retry qualifies. An uncertain connection failure is not replayed, and sending public response headers commits the response even before its first body byte. A one-slot endpoint or pinned launch never broadens to an unselected backup.

Its captured-identity, Node/undici and relay-owned OAuth examples do not establish CC Host's commercial implementation. CC Host's exact fingerprint/TLS stack and renewal algorithm remain unverified.

Earlier delivery history

The protocol, transport cleanup, numeric usage and recovered-node changes in the list below were delivered in client 0.2.1; they are not remaining blockers. This preserves the earlier audit history; the shared-edge activation gate mentioned there is a separate rollout from the current public Messages API.

  1. Fix direct backend WebSocket upgrade compliance without relaxing client TLS, pinning or HTTP-version checks.
  2. Close owned SSH transport on parent-only hard kill using a private liveness pipe and a live isolated group owner; do not signal a saved PID or caller group.
  3. Provide bounded numeric token/cache usage and explicit coverage, without request content or central model/session/device identity collection.
  4. Finish the recovered free node's queued runtime upgrade and verify secondary transport. Public routing activation still needs safe shared-edge conditions.

Client 0.2.2 adds semantic header-value normalization at both boundaries, opt-in read-only management MCP, explicit menu permission/model forwarding and side-effect-free background-job preflight. Cached quota observations carry numeric timestamps and exclude samples predating assignment/account change. Release status and live evidence must be checked separately; implementation tests alone do not establish production deployment or market superiority.

The current gateway adds separate endpoint credentials, own-slot single/multiple selection, sticky/priority routing, safe failover and direct HTTPS client setup. It changes the earlier fixed-slot-only comparison. Earlier bridge evidence should not be presented as proof that the new public model route has passed a live provider canary.

Remaining gaps: broader providers, team/commercial management, full account-wide management queries, physical-host redundancy and a sustained comparative user pilot. Each should be evaluated on actual usability/reliability evidence, not a promise to copy every competitor feature or prevent every possible metadata disclosure.
