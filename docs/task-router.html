Operator instructions · 18 October 2026

One Fleet entry point, explicit agent delegation

This pilot gives an outer agent a local JSON command interface and an optional stdio MCP facade for choosing either official Claude Code or Devin CLI. The chosen application runs a complete coding task on the operator's node. Fleet's existing model gateway, account assignments and signed laptop client continue to use their current paths.

Operator-only, disabled by default. This is a local pilot behind the operator's OS permissions. It has no customer endpoint, tenant isolation or billing integration. Do not expose the command runner to customers or advertise a working paid service based on these synthetic tests.

Prepare the native applications

Install and authenticate each application using its official workflow as the node's dedicated operator. Confirm that the selected account and plan permit the intended use, establish the pilot's billing limit, and choose an exact model identifier supported by that account. The router does not log in, inspect token contents, buy a subscription or switch accounts.

Devin's auth status command returned exit code zero when logged out in the observed 3000.11.92 build. The router therefore requires an operator auth_verified attestation and checks that the native credentials file exists with private ownership and mode 0600. It also runs auth status with output discarded and rejects a nonzero status. These checks do not prove token validity, model entitlement or subscription billing; native execution can still fail. See the official Devin authentication guide.

Review each workspace and its native hooks, plugins, MCP tools and permissions before setting trusted to true. Devin retains its native workspace-trust check. Installed Claude Code help states that print mode skips its trust dialog, so the explicit operator trust flag is required before a Claude task can start. The router adds no permission-bypass or autonomous flags.

Create one operator configuration

Save an operator-owned regular JSON file with mode 0600 or 0644, outside every selected workspace. Paths must be absolute and free of symlinks; use the resolved native executable paths. The state directory must also be outside the workspaces and is created privately. No credentials belong in this file.

{
  "version": 1,
  "enabled": false,
  "state_dir": "/home/operator/.local/state/ccfleet-task-router",
  "timeout_s": 300,
  "workspaces": {
    "pilot": {
      "path": "/home/operator/workspaces/pilot",
      "trusted": false
    }
  },
  "backends": {
    "claude": {
      "binary": "/home/operator/.local/share/claude/versions/VERIFIED_VERSION",
      "model": "EXACT_SUPPORTED_MODEL",
      "auth_verified": false
    },
    "devin": {
      "binary": "/home/operator/.local/share/devin/VERIFIED_VERSION/devin",
      "model": "EXACT_SUPPORTED_CLAUDE_MODEL",
      "auth_verified": false
    }
  }
}

The paths above are placeholders, not an installation recipe. Configure only the backends you have installed. After native sign-in, plan and billing verification, set that backend's auth_verified and the reviewed workspace's trusted to true, then explicitly set enabled to true. Omitting enabled keeps execution disabled. Unsupported fields, arbitrary commands and extra arguments are rejected.

Use the JSON command interface

Run from the installed Fleet repository, or install the Python package into the operator's environment. Give the outer agent the fixed configuration path and allowed workspace IDs. It supplies an explicit backend and a UTF-8 prompt file of at most 64 KiB. It cannot select an arbitrary directory, model, executable or extra CLI flags.

python3 -m ccfleet_agent.task_router --config /home/operator/router.json \
  start --backend devin --workspace pilot --prompt-file /home/operator/task.txt

python3 -m ccfleet_agent.task_router --config /home/operator/router.json status JOB_ID
python3 -m ccfleet_agent.task_router --config /home/operator/router.json logs JOB_ID
python3 -m ccfleet_agent.task_router --config /home/operator/router.json logs JOB_ID --stream stderr
python3 -m ccfleet_agent.task_router --config /home/operator/router.json list
python3 -m ccfleet_agent.task_router --config /home/operator/router.json stop JOB_ID

start returns a job ID and the configured selected_model. Poll status and read the bounded logs as needed. A completed process is not proof that the code change is correct; inspect the result and run the project's checks. If submission times out or its outcome is uncertain, list existing tasks and resolve the record before submitting again. There is no retry, queue, cross-provider fallback or create-request idempotency guarantee.

Set enabled to false to block new tasks. The supervisor checks configuration authorization every 15 seconds and stops a task if its exact configuration binding changes or becomes unavailable. Immediate cancellation uses stop. Keep the state directory path and readable configuration available for status and stop operations. Configuration edits do not roll back project files.

Connect the outer agent through local MCP

The optional facade uses stdio and exposes task tools separately from Fleet's existing read-only management MCP. Launch it on the operator node with the same fixed configuration:

python3 -I /installed/ccfleet/ccfleet_agent/task_mcp.py \
  --config /home/operator/router.json

Configure the outer agent to run this fixed command as a local stdio MCP server. There is no network listener or remote customer authentication layer. The installed path above is a placeholder for the operator's reviewed Fleet checkout.

  • fleet_agents {} lists configured adapters and selected models.
  • fleet_task_start accepts backend, workspace, prompt and a caller-generated request_id. It accepts no executable paths, extra flags or model override.
  • fleet_task_status and fleet_task_stop take a job_id.
  • fleet_task_logs takes a job_id, optional stream and optional bytes; logs are returned only when requested.
  • fleet_tasks {} lists private task summaries.

For a start request, use an opaque UUID as request_id and retain it. Repeating the same request ID with identical task inputs returns the recorded job rather than resubmitting the task. Changing inputs under the same ID is rejected. If a start outcome is unresolved, inspect existing tasks and resolve it with the operator; using a new request ID would authorize another task. Closing the MCP process leaves an existing task under its supervisor; use fleet_task_stop to cancel it.

What the pilot bounds

ControlBehavior
Concurrency and durationOne active task across both adapters; 300 seconds by default, configurable from 1 through 900 seconds. Unknown cleanup blocks the next task until reviewed.
Process supervisionThe existing local-job guardian controls the owned process group, confirmed cancellation and timeout. The router never restarts a provider task.
Native authenticationCredentials remain in native home locations. Inherited provider API keys, model overrides, routing variables, permission overrides and Python startup variables are omitted from provider children.
Private recordsJob specification, prompt, state and logs stay in mode-0700 task directories. Each stdout/stderr log is capped at 4 MiB. History holds at most 256 records; archive completed records using the existing local-job operator facilities before capacity is exhausted.
Devin session settingsA private generated config requests the configured model, disables automatic installation of updates and disables Devin subagents. The native ATIF export is private and may contain full task content. Its size is not capped by the log limit.
Model and spend evidenceThe router records the selected model. Provider-reported actual model and billable use need separate verification. Timeouts and disabled subagents do not create a dollar, token or subscription quota guarantee.

The workspace allowlist constrains routing input; it is not a filesystem sandbox. Each native agent has the operator OS user's authority and can access that user's files, credentials, network and task records subject to its own permissions. Same-user processes can alter those records. Use a dedicated pilot user and reviewed workspaces. This is insufficient for untrusted customer tasks or shared subscription access.

Devin's model/configuration and export behavior follow the official configuration reference and commands reference. Choosing a Claude model in Devin runs Devin's application; it does not authenticate the standalone Claude Code binary with a Devin subscription.

Verification and rollout status

The automated suite uses synthetic executable fixtures and local subprocesses to verify adapter arguments, private files, success and failure, authentication rejection, native trust failure, cancellation, timeouts, single concurrency, strict configuration, workspace selection, capped logs and provider environment filtering. It makes no provider calls. Real account sign-in, plan entitlement, billing, actual model use and a paid end-to-end task remain operator pilot checks.
