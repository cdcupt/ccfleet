Back up, move or recover the Fleet server

The website, HTTPS gateway and internal broker form one deployment. The primary and broker share the same SQLite file and volume; this is not a replica on a second host. Only the primary runs monitoring and outage email, but broker authorization and revocation can also write to the shared database. Keep one authoritative writable deployment.

Use the live service environment. A server CLI command below means the CLI inside the current primary, with its actual environment and CCFLEET_DB. In this repository's Compose example:

docker compose -f deploy/docker-compose.yml exec -T ccfleetd ccfleetd node list

Use the actual project name, service name and Compose files for your deployment. A native installation must load the running service's environment. Do not accidentally run a host CLI against its default path or a spare copied database.

Back up SQLite safely. A live database uses WAL: recent commits may be in -wal, so copying only the live .db is unsafe. Use SQLite's online backup API, check integrity, and keep the completed backup private. This example creates a unique 0600 backup as the service user:

docker compose -f deploy/docker-compose.yml exec -T ccfleetd python - <<'PY'
import os
import sqlite3
import time

os.umask(0o077)
live_path = os.environ["CCFLEET_DB"]
backup_path = live_path + ".backup-" + str(time.time_ns())
source = sqlite3.connect("file:" + live_path + "?mode=ro", uri=True)
destination = sqlite3.connect(backup_path)
try:
    source.backup(destination)
    if destination.execute("PRAGMA integrity_check").fetchone() != ("ok",):
        raise SystemExit("backup integrity check failed")
finally:
    destination.close()
    source.close()
print(backup_path)
PY

Copy completed backups to a protected off-host location and compare checksums. Backups, environment files and private keys never belong in the repository or public reports. Package public reference HTML as regular, single-link 0644 files and verify the built image can load it as UID 10001; the library rejects group/world-writable documents.

Move the server without splitting state.

  1. Prepare the tested images, private volume, TLS edge and configuration on the new host. Keep a copied primary unstarted: serving it starts a monitor, updates state and can send emails. Preserve the public URL, cookie/OAuth secrets, account and slot records, device grants and gateway claim bindings.
  2. Verify the new host can reach every configured node SSH port with the existing host-key pin. Update any source-address firewall allowlist narrowly. Reporting over the same public HTTPS URL needs no node change; a fixed-IP reporting tunnel needs its target and independently verified server pin updated. Native Claude credentials, histories and projects remain on their existing slots/computers.
  3. Pause new Fleet work and drain active model, SSH and WebSocket streams. Stop both source primary and broker and fence their automatic startup and deployment paths. Take the final backup from the stopped volume with a SQLite-only helper, not a serving copy. For the example above, replace its first line with docker compose -f deploy/docker-compose.yml run --rm --no-deps -T --entrypoint python ccfleetd - <<'PY'. The helper inherits the volume and environment without starting ccfleetd. Verify integrity, transfer the completed backup, compare checksums and durable account/slot/device/key projections before first serve.
  4. Give the new data volume its service ownership (UID 10001). Keep the dedicated inference-only SSH key mounted read-only, owned by that UID with 0600 mode and a 0700 parent. Preserve per-key forced commands, no-PTY/no-forwarding controls and node pins; never substitute an operator, device or provider credential. Start one primary; start the same-volume broker with CCFLEET_BROKER_ONLY=1 and its gateway and machine metrics disabled. An HTTP /healthz 200 can precede Docker's first 60-second health check; wait for healthy and fresh reports from every node.
  5. Route the public hostname to the new deployment. A temporary old-edge forward must also send all Fleet requests there while the old apps stay fenced. Verify TLS using the public hostname before DNS changes; for an HTTPS forward, set tls_server_name and upstream Host to that hostname and never skip certificate verification. Retain Fleet's named access-log discard and scoped http.log.error.fleet discard. Validate before reloading an edge; for a shared source edge, coordinate upgraded streams across all tenants and verify the other domains after changing only Fleet's routing.

Health, pins and state preservation do not prove a model request succeeded. Readiness checks make no model call. If no active gateway grant exists, do not enroll a new account or key merely to obtain a passing migration probe.

Rollback with current data. After the new deployment accepts heartbeats or user changes, the old snapshot is stale. Prefer a schema-compatible image rollback on the new host after backing up its current database. To move back, drain and fence the new primary and broker, take a fresh WAL-safe backup, verify and restore that current state, then start only the restored deployment and switch routing. Never reactivate the source's stale database or overwrite legitimate new activity to force an old baseline comparison.

Move connections to the canonical domain

The public service address is https://ccfleet.io. Retain the previous domain as an explicit HTTPS/API and secure WebSocket compatibility alias while older clients are in use. Browser pages may redirect; authenticated APIs, WebSocket upgrades, node heartbeats and OAuth callbacks must retain their direct behavior.

Signed client 0.2.6 resolves only the exact known legacy HTTPS/WSS authority at the outbound boundary. It keeps raw saved pairings, endpoint secrets, key IDs, slot choices, provider configuration and native history in place. It does not follow an authentication redirect or retry a failed canonical request through the old host. Custom deployments and loopback transports retain their own origins. Fresh pairings default to the canonical domain.

Publish the immutable signed manifest before advancing the signed stable channel. Verify every committed bundle digest and preserve all older signed artifacts. The installer’s --next option verifies the fixed signed 0.2.6 manifest and installs a separate ccfleet-next wrapper over its own managed release directory. It does not replace the usual launcher or change pairing, native Claude, shell configuration or active processes. Use the existing connection for the domain trial; pairing or replacing a key is a separate account change. The normal ccfleet update and ccfleet update --rollback commands remain available. Fleet 0.2.7 adds upgrade as an alias, root -v/--version, local -c/-r, and preferred --permission-mode with --mode retained. Existing clients obtain these spellings through ccfleet update; no re-pairing is required. The fixed 0.2.6 trial does not acquire these new aliases merely by installing --next. See the current command reference.

For client recovery, ccfleet list --remote fetches current own-slot names; the default list remains saved pairings. A working paired slot can authorize gateway setup --provider devin for exactly one verified own slot. Use the CLI provider-selection recipe; native runtime preparation and account verification still come first.

For an existing shared machine, inspect the effective service configuration before changing its reporting URL. The agent loads /etc/ccfleet/agent.env, then lets process environment override it. Require the expected enabled machine identity, an idle one-shot service and its existing state lock, a private root-owned file and no URL override. Back up the exact file privately and atomically replace only the literal CCFLEET_URL value. Preserve token and all other bytes, owner and permissions. Let the next ordinary timer run load the new URL; do not restart active sign-ins, provisioning, native sessions or broker connections. Verify a fresh successful heartbeat and the effective canonical URL. Leave disabled machines and loopback/tunnel configurations alone.

Naming machines and slots

One machine is one slot. Its authenticated node ID and slot ID remain stable; its display name and desired hostname follow the slot's lifecycle. Choose initial IDs by role:

  • <operator>-N for the operator's own machines, owner nodes and shared machines kept for their own account alike: erik-1, erik-2;
  • pool-N for shared machines offered to customers: pool-1, pool-2.

A shared machine's one slot normally starts with the same ID as its node (pool-1 on pool-1), and its Linux user is slot01. When somebody claims it, the slot gets a neutral name, slot-4821 (random digits nobody answers to yet), never anything from their address: Claude Code can report the hostname to Anthropic (Erik, 2026-09-24). The holder renames it on their page, and ccfleetd slot name <slot> [<name>] does it for them (no name: a fresh neutral one). A handle set with ccfleetd account handle <email> <handle>, only at the person's request, names their slots <handle>-<n> instead (alice-1, then alice-2). The machine takes the name as its hostname on its next run; the console marks the machine "hostname pending" until it has. When the wipe that frees the slot completes, the name goes and the slot receives an unused pool-N name. The pool name remains reserved for that slot across later claims and releases; an existing pool-N identity is retained when available. The authenticated node and slot IDs do not change, so installed agents, SSH pins and history keep their existing identities. A failed or unfinished wipe never makes the slot free or publishes it as a new pool slot.

In the operator console, a confirmed free, holderless machine slot uses only its pool-N name in the Fleet row, Slots row and Manage heading. Internal node/slot IDs, owner and region remain under the Slots row's Manage controls. Reservations remain visible as a warning and retain their account details under Manage; cleanup and health warnings remain. Retired or disabled machines are omitted from the normal catalogue; their underlying records remain available for operator recovery.

New node and slot IDs must not reuse an existing slot's reserved pool name, including while that slot is held. Check the current names in the console before registering another machine; choose an unused ID if a pool name is already reserved.

The public status page lists monitored slot machines in a compact table with Machine, Status and Last report columns immediately before Reading this page. Each machine keeps a stable Machine N label, and the holder's slot card links to that row. Signed-in operators see the actual machine name beside its neutral label. Status describes machine health only; the table does not include detailed reasons or per-machine uptime cards. Public visitors do not see holder names, account state or raw alerts.

Set the hostname when the machine is added, the way step 4 of Rename a machine does, so a provider's serial-number hostname never reaches the picker. A fleet already running under other names moves onto these with Rename a machine, held slots included.

Read public output speed

The Status performance panel shows streamed output rate after twenty eligible replies have been measured. It divides the final provider-reported output-token counts by their matched first-to-last body-chunk delivery time observed at the node for native/bridge traffic or at the HTTPS gateway. Gateway traffic is not counted twice. This excludes the initial wait and includes stream pauses, network transfer and reported thinking or tool-output tokens. Compare equivalent models and workloads; it is an observed delivery rate, not isolated model generation speed or peak fleet capacity.

Only fully completed successful streaming Messages replies with valid final usage, multiple nonempty chunks and at least 100 milliseconds of measured delivery contribute. Single-chunk, too-short, malformed, interrupted, rejected, non-streaming and token-count replies supply no speed sample. Buffering can affect the observed rate. Native/bridge samples require fresh, valid reports for the current holder and bound Claude account; old or unsupported agents leave those samples unknown. Older slot token totals and timing averages cannot be used to reconstruct historical TPS.

A dash means no publishable speed measurement yet. Normal eligible traffic fills the counter; opening Status does not issue a model request. Node observations remain in the private account-bound seven-day relay file and numeric heartbeat fields. The server's gateway recorder keeps only anonymous UTC-day sample counts, output-token sums and duration sums in gateway_throughput_days, over the seven-date reporting window. Old days are filtered immediately and pruned on new samples and by the hourly monitor. No account, slot, model, prompt, response, credential or individual event timestamp is stored there.

The bounded background recorder drops unusable samples or exhausted contention attempts; telemetry failures do not replay inference. Published sample counts describe measured coverage. The added table is compatible with the previous server image. Recovery must keep the latest consistent database; do not replace it with an older snapshot merely to clear telemetry.

The public homepage usage ranking separately publishes measured token totals, model details and estimated standard API-equivalent USD values under partly masked user-chosen nicknames. Short nicknames are fully masked; missing nicknames use a generic label. Emails and account IDs are never public-name fallbacks. The primary ranking token total and estimate use the same priceable cohort. Output and reply counts remain in expanded details. Broader reported totals and older/unpriced tokens appear there, under a clearly separate scope. K/M/B mean thousand/million/billion; exact counts remain in tooltips, while reply sample counts stay precise. Processed totals include cached context counted again on each request; they are not generated or unique text. Estimates use reported model labels; these numeric aggregates retain no raw replies and cannot reliably reprice older model/fallback attribution. Masking is not anonymity. Estimates are not Claude Pro/Max bills or amounts paid; measurement, model-price and cache coverage are shown, and missing or unpriced usage is unknown rather than zero. Existing validated aggregate tokens can remain visible without a model price; model details and cost estimates require new model-aware observations. Older model detail is not backfilled. See Privacy for this distinct public disclosure.

Add an owner

  1. server: ccfleetd node add <node-id> --owner <name> --region <region> [--rc-expected] and hand the printed three lines to the owner over a private channel.
  2. New VPS in a supported region. root: bootstrap.sh <owner> <pubkey>.
  3. node: git clone https://github.com/cdcupt/ccfleet.git && ccfleet/node/setup-owner.sh, fill ~/.config/ccfleet/agent.env, chmod 600 it.
  4. node: log in over SSH, which attaches you to the persistent session, then claude, /login, paste the code, /status.
  5. node: ccfleet-agent --print, then systemctl --user start ccfleet-agent.service.
  6. server: ccfleetd node pin <node-id> <version> with the version from /status.

Add a shared machine

A shared machine carries one slot: its own Linux user with its own Claude sign-in, under a name its holder chooses. root here means root on the new machine; laptop is wherever your operator SSH key lives.

Pick the box. A KVM VPS running Debian or Ubuntu with at least 2 GiB of RAM. LXC and OpenVZ containers are unsuitable: every slot needs its own systemd user manager. Size it from what a slot really uses (measured 2026-09-23 on a signed-in slot): about 420 MiB idle, about 665 MiB while a session runs, and about 225 MB of disk for Claude Code; the OS and the machine agent take about 400 MiB. So a 2 GiB box carries its one slot with room to spare. Below 4 GiB, add a 2 GiB swap file as a cushion for spikes.

  1. laptop: make a key for this machine and install it for root, e.g. ssh-copy-id -i <key> root@<machine> while password login still works.
  2. Prove key login before anything turns passwords off. Some provider images ship with key login disabled (PubkeyAuthentication no at the end of /etc/ssh/sshd_config). root: sshd -T | grep -E '^(pubkeyauthentication|passwordauthentication) '; if key login is off, set PubkeyAuthentication yes there, sshd -t, reload ssh, and log in again with the key before going on.
  3. root: harden with bootstrap.sh, not install.sh (that one turns the box into a single owner's node, whose agent machine-setup.sh refuses to run beside): git clone https://github.com/cdcupt/ccfleet.git && ccfleet/node/bootstrap.sh <your-login> "<your public key>". It gives you a login with sudo, key-only SSH, a firewall and unattended security upgrades, and it stops, leaving SSH as it was, if sshd would not end up with keys on and passwords off. Then name it and put its clock on UTC: hostnamectl set-hostname <machine> && timedatectl set-timezone Etc/UTC. Claude Code can tell Anthropic the machine's time zone; UTC says nothing about where the slot's holder is, and the pages show times in each viewer's own zone.
  4. root, only below 4 GiB of RAM: fallocate -l 2G /swapfile && chmod 600 /swapfile && mkswap /swapfile && swapon /swapfile, then echo '/swapfile none swap sw 0 0' >> /etc/fstab and echo vm.swappiness=10 > /etc/sysctl.d/99-ccfleet-swap.conf && sysctl -p /etc/sysctl.d/99-ccfleet-swap.conf.
  5. server: ccfleetd node add <machine> --owner <your-login> --region <region>. The token it prints is shown once; keep it for step 8 and nowhere else.
  6. server: ccfleetd node pin <machine> latest, the Claude Code channel the machine's slots are meant to follow. Slots start on opus, which is the newest Opus only on a Claude Code that knows it.
  7. server: ccfleetd slot add <machine> --machine <machine> --unix-user slot01. Its capacity stays 1: a second slot is refused because the machine has one hostname and one advertised access endpoint. Do not create the Linux user yourself: the machine makes it when somebody claims the slot and wipes it when they give it back.
  8. root: curl -fsSL https://raw.githubusercontent.com/cdcupt/ccfleet/main/node/machine-setup.sh | bash -s -- --server <fleet url> --node <machine> --token <token>. This also installs git, gh, rsync and the forced CC Fleet entrypoint, creates the root-controlled /etc/ccfleet/authorized_keys directory, and validates an sshd match block that forces that entrypoint and disables agent, port and X11 forwarding, tunnels and user rc files for the ccfleet-slots group before reloading SSH.
  9. root: copy /etc/ssh/ssh_host_ed25519_key.pub to a root-owned file on the CC Fleet server over an authenticated operator channel. server: configure the endpoint that only the broker uses: ccfleetd node access <machine> --host <address-reachable-from-server> --port 22 --host-key-file <copied-public-host-key>. Do not put the node address on the customer page.
  10. server: within a couple of minutes ccfleetd slot list --machine <machine> shows its slot free and on machine no: the machine itself has confirmed it is empty, which is what makes it claimable.

Prove the machine is closed before anyone is given a slot on it:

  • laptop: ssh -o PubkeyAuthentication=no root@<machine> is refused with Permission denied (publickey).
  • root: sshd -T reports pubkeyauthentication yes and passwordauthentication no.
  • root: sshd -T -C user=slot01,host=localhost,addr=127.0.0.1 (after the first slot has been provisioned) reports the forced slot-entry.sh, the root-controlled authorizedkeysfile, allowagentforwarding no, passwordauthentication no, kbdinteractiveauthentication no, allowtcpforwarding no, x11forwarding no, permittunnel no and permituserrc no.
  • root: passwd -S slot01 reports P, not L. The password is random and discarded; the sshd checks above are what keep password login impossible.
  • root: /etc/ccfleet is root-owned 0711, its authorized_keys directory 0755, and each public-key file 0644; none is holder-writable. /etc/ccfleet/agent.env remains root-owned 0600.
  • root: ufw status reports Status: active, and systemctl is-active ccfleet-machine.timer says active.

Slot holders are not given an SSH workflow or the node address. They install the ccfleet command, pair a device from /account, and run ccfleet. Under the surface the client opens SSH through the CC Fleet WebSocket broker. Every key has a forced command and forwarding disabled. After a test pairing, inspect /etc/ccfleet/authorized_keys/slot01: it must name slot-entry.sh and the no-forwarding options. The slot's own ~/.ssh/authorized_keys is not an sshd key source. Remove the device from the page and confirm the managed file is removed on the next machine-agent cycle.

The packaged ccfleet-shell.service and slot-entry.sh both launch Claude with --dangerously-skip-permissions; the default unit also passes --model opus --effort max. On rollout, the slot agent replaces an older unit and ends the old ccfleet tmux session once; the holder's next ccfleet command creates the new default session. Verify the slot still has no sudo or privileged group before calling that safe enough to operate. The forced entrypoint also accepts only ccfleet-session with a validated action, session name, Claude permission mode, model and effort. Test that arbitrary commands are rejected, then test ccfleet new research --model fable --effort xhigh --permission-mode plan, ccfleet attach --session research, in-session /model and /effort, and an explicit restart.

For a computer configured by the old ccfleet-connect flow, have the holder create a fresh pairing code and run:

curl -fsSL https://raw.githubusercontent.com/cdcupt/ccfleet/main/laptop/install.sh | bash -s -- --migrate

The migration pairs first and calls the installed legacy command's --remove only after success. It cannot revoke the Anthropic setup-token; the holder does that in their Anthropic account if the token is no longer used anywhere.

These steps are deliberately mechanical. An operator can put exactly them in a private script that takes an address and a name, reads the root password once from a prompt, and re-runs safely, so the next machine is one command.

Native Devin operator pilot

Reviewed October 18, 2026; operator-enabled pilot. The account page offers Devin only after the holder's own slot is verified; Anthropic remains the default. The private four-step Read/Edit/Bash fixture passed three tests and returned its answer. Seven finalized provider requests were verified as Opus 5.5 Max. This is private pilot evidence; public Fleet endpoint checks must be recorded separately. Verify that path separately before expanding the pilot. See the short Devin explanation and route diagram.

The route is local official Claude Code → the same Fleet Messages API → native Devin CLI on the holder's assigned slot. The website provider setting preserves the endpoint and key token. An internal stdio MCP bridge exposes the exact caller-declared tool catalogue. A genuine tool call returns to Claude Code for local permission checks and execution; the bridge never executes Read, Edit or Bash on the node. Each explicit Messages continuation starts a fresh native session with the complete supported visible history, including prior tool results.

Compatibility contract: native-agent-v1 passes visible system instructions and history as labeled context. Native harness authority still applies. Unsupported images, documents, historical thinking/signatures, server tools and unsupported request controls reject before launch. /v1/messages/count_tokens returns 501. max_tokens is passed as context, not an enforced output or spending cap. Replies are buffered before Messages/SSE delivery. Missing usage stays unknown; observed token counts, finalized provider records and quota changes are not a billing total or guarantee.

  1. Keep activation explicit. The server requires CCFLEET_GATEWAY_DEVIN_ENABLED and the exact approved CCFLEET_GATEWAY_DEVIN_NATIVE_VERSION, CCFLEET_GATEWAY_DEVIN_ADAPTER_REVISION and CCFLEET_GATEWAY_DEVIN_MODEL_MAP_DIGEST. The existing gateway/service SSH-key controls remain required. Defaults and installers do not enable Devin, create provider accounts or supply credentials. Allow only an explicitly approved own-account, one-node slot; no operator account pool or shared subscription.
  2. Register root-owned policy on the node. Under /etc/ccfleet/devin/<slot-user>/, profile.json has exact fields version (1), enabled (true), config_path/config_sha256 for metadata.json, template_path/template_sha256 for template.json, verifier_user, and source_profile_path/source_profile_sha256. Keep root ownership and non-writable ancestry; give the intended verifier only the read/traverse access it needs. The template uses the real slot UID/HOME; metadata uses the separate verifier UID/HOME. Both bind the same current owner and rental claim, approved native executable SHA, adapter SHA and canonical model map. Derive the model digest from model_uid, sorted request_models and sorted verified_models. The NativeConfig manifest pins the adapter, ACP controller, MCP helper, tool codec, relay, inference policy, egress module, package source, Python/native executables and native configuration. Preserve its native-tool denials and exact MCP hook. Native settings must include the integer version: 1 before pinning: an unversioned file can be migrated and rewritten by native startup, invalidating its digest. Verify a model-free startup leaves the pins unchanged before authorizing a prompt; never accept changed slot bytes automatically.
  3. Preserve the chosen network exit. Native inference and metadata receive only the protected node proxy environment. Incomplete proxy configuration rejects before launch. On a proxy-routed node, include the dedicated verifier's actual UID in persistent IPv4 and IPv6 egress enforcement; ordinary-slot UID ranges do not cover system verifier UIDs. Verify the exit and direct-network denial before registering readiness. Upstream credentials remain root-only.
  4. Verify identity outside the holder's UID. A dedicated ccfleet-devin-v* verifier must have a different unprivileged UID, non-root GID, a nologin/false shell and no privileged or slot groups. It must run no customer processes. Holder-owned slot JSON or same-UID stdout cannot attest readiness. Root snapshots only the fixed native credential file, without following links, into the verifier's private HOME as an exclusive 0600 file. The collector creates a fresh credential-only HOME and runs the pinned auth status and models list --format json commands. It verifies the stable provider User ID under the trusted API origin and the selected model in the live catalogue. No inference is needed for this check.
  5. Pin the source of that proof. The root source profile records metadata_profile=native-auth-status-fresh-home-v1, native version/SHA, trusted API origin, collector SHA, adapter revision, model-map digest, capability evidence, live_subject_source_verified and the reviewed proof digest. The private devin_account.py --collect-profile pipe accepts only the root registration, runtime and binding. Root compares its private credential digest with the snapshot and rechecks the original slot bytes afterwards. Remove the snapshot only after confirmed cleanup; uncertain cleanup leaves it quarantined and verification denied. Raw credentials, user IDs and emails stay on the node. The credential hash detects changes; it is never account identity.
  6. Publish only bounded, current authority. devin_provision.py produces the eight-field public report: account_fp, identity_verified, bridge_contract, capabilities, native_version, adapter_revision, model_map_digest, observed_at. The authenticated root machine reports it for the current claim; it does not set Claude logged_in. Private proof is cached for at most 240 seconds, with credential/profile checks on fast polls. Current server key and owner/claim/provider generations produce root-owned 0640 per-key config/grant files named by SHA-256 of the key ID. Grants also bind the stable account fingerprint, runtime, config SHA, private credential change guard and observation time.
  7. Validate the route before offering it. The fixed service command ccfleet-devin-gateway-v1 enters devin_relay.py --gateway-protocol-v1 with isolated Python. Its status check is model-free admission from a fresh root grant, at most 300 seconds old. devin_native.py still requires an actual owned MCP initialize/initialized handshake before any prompt. Default CLI plan modes are inert. After metadata, test the unchanged local Claude Code client through the public endpoint, full history, local tool loop, cancellation and revoked access under an explicit pilot budget. A healthy website, metadata success or private fixture alone does not establish this public path.

Revoke and recover: remove/disable the root registration or grant when the claim, owner, key generation, runtime, login or credential changes. The root reconciler revokes stale authority before replacement, including when the next heartbeat fails. Missing, expired or mismatched grants deny inference; there is no provider fallback or automatic replay after an uncertain attempt. Confirm child cleanup, repair the root policy, then acquire fresh native metadata. Never restore old credentials or mark a holder-supplied report verified to force readiness. Keep private proof and accounting out of public status and support logs.

Each owner uses their own account on one node. Devin Pro/Max are single-user plans with quotas. Resale or a bundled subscription requires Cognition's written permission; that approval is pending and no Devin package is for sale. Recheck official plan details and usage restrictions before commercial activation.

USD slot service credit

CCFLEET_USD_SLOT_CREDIT_ENABLED defaults to off. Enable this mode only after its server release and database-clone checks have passed. It changes new customer acquisition from a slot-count allowance to a confirmed monthly purchase using internal USD service credit. It does not convert old manual payments, charge existing holders, or turn a provider subscription into a shared plan.

  1. Sign in to the admin console with a real administrator account. A configured admin token has no named database actor and cannot issue credit.
  2. Open Accounts, select the exact customer, enter a USD amount and a one-line reason, and confirm the grant. The immutable ledger records the actual administrator. Retrying the same request cannot add the grant twice.
  3. The customer opens Your slots, checks the balance, chooses a machine in Available slots and reviews its current monthly price. A purchase checks funds, current quote, reservation and machine readiness in one transaction. A changed quote requires a fresh confirmation.
  4. The purchase pays for one calendar UTC month starting at purchase. Renewal requires the same current claim and another explicit confirmation; it extends the paid end or starts from the present if already expired. No automatic debit or reload runs.

After a paid claim expires, new Fleet access is paused until renewal; requests admitted earlier continue under the existing identity and revocation checks. Expiry never releases or wipes a slot. Existing claims without a wallet purchase remain grandfathered. Node SSH authorization refresh is heartbeat-driven; do not describe this as instantaneous removal of every previously published direct-SSH key.

After a slot has a purchase or renewal record, its internal node and slot IDs cannot be renamed or deleted. The billing history keeps those original identifiers. Customer-facing display names can still change; disable or retire a machine instead of removing its identity record.

The local credential-free CONNECT endpoint is http://127.0.0.1:912; it preserves provider TLS validation and does not terminate provider TLS. Upstream scheme accepts http, https, or authenticated socks5. Use only the protocol and port documented for the purchased allocation. Timers never run after setup

setup-owner.sh now refuses to continue when the owner has no working per-user systemd manager, because enabling a timer there looks successful and then nothing ever fires. The usual cause is a minimal image without libpam-systemd, so pam_systemd.so is absent and XDG_RUNTIME_DIR is never set.

  1. node: systemctl status user@$(id -u).service and journalctl -u user@$(id -u).service -n 20.
  2. root: apt-get install -y libpam-systemd && loginctl enable-linger <owner>. This edits PAM, so keep a second SSH session open while you do it.
  3. Log out, back in, re-run setup-owner.sh.

credentials_missing or token_expired

For hosted slots, first distinguish access renewal from a longer-lived login that needs authorization. The slot page and console show the latest verified observation; a stale heartbeat cannot prove recovery.

  • Renewal pending: native maintenance is retrying a temporary failure, or access expiry has not yet advanced. Inspect the fixed renewal outcome, probe-start observation and next-attempt timestamp. A busy probe is not a failed login. Preserve the slot, its files, pairing and credential store.
  • Login expiring: a known longer-lived login expires within three days. Ask the holder to complete Sign in again before it expires. Current access is reported independently; its timestamp does not establish live provider acceptance.
  • Sign-in required: native Claude explicitly reports an expired or rejected login, or access is unusable and refresh capability is absent or expired. The holder must authorize a fresh login. Do not restore a copied old refresh token or change the slot's bound account.

Fixed outcomes contain no native pane text, credential values or provider response bodies. Unknown errors remain unconfirmed renewal; diagnose them without publishing raw output. These credential alerts do not trigger machine outage emails. Legacy owner nodes follow the sign-in procedure below.

The owner needs to sign in again; nobody else can do it for them.

  1. The holder opens /account, presses Sign in again, completes Anthropic's browser flow and pastes the code back into the page.
  2. The machine applies the result to the slot; nobody else handles the credential.
  3. The alert closes on the next heartbeat.

token_stale

Usually the slot was simply idle for a day (Claude Code refreshes on use). Run ccfleet; if the warning persists after use, treat it as token_expired.

no_heartbeat

  1. server: ccfleetd node list to see the last time it was heard from.
  2. node: systemctl --user status ccfleet-agent.timer ccfleet-agent.service, journalctl --user -u ccfleet-agent.service -n 50.
  3. Common causes: linger disabled (loginctl enable-linger <owner> as root), wrong token after a rotation, VPS down.

version_mismatch

The pin is now authoritative: an agent that finds its node on a different version installs the pinned one and reports the result. So this alert means the node has not reconciled yet, or tried and failed.

  1. server: check the node's row. A failed attempt is shown under the version with the installer's own error.
  2. A node that simply has not caught up closes the alert on its next heartbeat.
  3. Repeated failures back off for an hour between attempts, so a node that cannot install the pinned version alerts rather than retrying in a loop.

Upgrading a node by hand no longer sticks. While a pin is set, the next heartbeat installs the pinned version over whatever you just installed. Change the pin instead; the node follows. To work on a node outside the pin, either clear the pin or run its agent with --no-reconcile.

Staged upgrade of the fleet

The pin drives the upgrade, so stage it one node at a time and let each one prove itself before the next.

  1. server: ccfleetd node pin <first-node> <new version>. Pick the node you would least mind losing for an hour.
  2. Wait a full heartbeat interval and confirm the row shows the new version with no failure. Then work a normal session on it for a day.
  3. Pin the remaining nodes. Never pin them all at once: a bad release would take the whole fleet in the same five minutes.

A node can also be told to track a channel — ccfleetd node pin <node> latest or stable. The server reads both channels' release numbers from Anthropic about hourly and sends them with every reply, and the node installs a new release at its next quiet moment, never during a sign-in. Without a number from the server it resolves the channel itself once a day. A channel pin never reports drift, because tracking it is what the pin asks for.

egress_changed

Confirm with node exitip. If the provider moved the IP, nothing to do; the alert is informational and closes on the next heartbeat. If you did not expect it, check the VPS console for a rebuild or migration.

disk_high

node: du -sh ~/.claude ~/backups ~/projects 2>/dev/null; old backups rotate automatically (CCFLEET_BACKUP_KEEP); ~/.claude/debug and ~/.claude/cache are safe to delete.

remote_control_down (legacy owner nodes only)

node: systemctl --user restart claude-remote-control.service, then tmux -L ccfleet-rc attach -t remote-control to read the reason. Remote Control needs a valid login; if it complains about eligibility, do the re-login runbook. The very first start must be interactive to accept the one-time prompt.

Hosted customer slots disable and stop this legacy unit. Do not turn it back on; the supported customer path is the local ccfleet terminal.

slot_wipe_failed:<user>

A slot was given back, or taken back, and removing its Linux user failed. It stays out of the pool, because only a finished wipe makes a slot free, and the machine agent tries again every 10 minutes by itself. The alert names the error. The usual cause is a process that outlived pkill; to see it, on the machine: ps -u <user>, and the agent's own account of it with journalctl -u ccfleet-machine --since -1h. Once the cause is gone, either wait for the next attempt or run it now as root: /usr/local/lib/ccfleet/slot-remove.sh --slot <user>. The slot turns free when the machine next reports the user absent.

slot_occupied:<user>

ccfleet's records say the slot is free, but the machine says its Linux user exists. It is not handed out while that is true: a user that should not exist may still hold the last person's files. Nobody made it through ccfleet, so it was made by hand, or the fleet's database was restored from before a claim. Look at what is in the home directory before anything else. A leftover slot comes off with /usr/local/lib/ccfleet/slot-remove.sh --slot <user> on the machine. If that refuses because the account is not a ccfleet slot, the name belongs to an account ccfleet did not make: leave that account alone, remove the slot here with ccfleetd slot remove <id> (it is free, so it may go), and declare it again under an unused name.

slot_missing:<user>

Somebody holds the slot, and its Linux user has gone from the machine: removed by hand, or the machine was rebuilt. Their files went with it. Take the slot back in the console (it asks for the slot's id), tell the person, and let them claim again; the new slot is set up from scratch.

slot_provision_failed:<user>

Setting up a claimed slot failed, so the claim was given up and the slot is being wiped; the person can simply claim again. It is a warning, not a page, unless it repeats. Repeats mean the machine cannot make slots at all: read the error in the alert, then journalctl -u ccfleet-machine --since -1h on the machine. Disk space and a failed Claude Code install are the usual causes.

quota_high_session or quota_high_week

The account's Claude usage window is 75% used (warn) or 90% (critical); the thresholds are CCFLEET_QUOTA_WARN_PCT and CCFLEET_QUOTA_CRIT_PCT. Nothing is broken and nothing on the node needs doing: the owner slows down or waits for the reset the message names. The windows belong to the Claude account, counted across every device it is used on, so the node is only where it was noticed. A reading older than two hours is ignored rather than alerted on.

account_elsewhere or account_elsewhere:<user>

One Claude account is signed in on two live places at once: two slots, or a slot and a node. ccfleet keeps one account in one place, so the alert is raised on each place, and the message names the other. An owner's node carries it with nothing after the colon; a slot carries its Linux user.

  1. Find out whose account it is and which place should keep it. Usually one person signed a slot in with the account already on their own node.
  2. Sign it out of the other place. On an owner's node, the owner runs claude auth logout there, then signs that node in to its own account. A slot on the wrong account moves to another of its holder's accounts with Change account on their page, files kept, at most once a week; or it is given back (a wipe) and a new one claimed with the right account.
  3. The alert closes on the next report from the place that stopped reporting the account. A node gone quiet counts as nowhere: it is left out rather than counted twice.

account_changed:<user>

A held slot is signed in to another Claude account than the one it keeps. Nothing in the product does that: Sign in again keeps only the slot's own account, and Change account moves the binding along with the sign-in. So its holder signed in by hand, or put another account's credential in place. The slot is their own Linux account, so ccfleet detects this; it cannot prevent it.

  1. Ask the holder to sign the slot's own account in again from their page, or, if the other account is the one they mean to use, to move the slot to it with Change account. Either is kept only once it has worked, and replaces the wrong sign-in.
  2. If they will not, it is the terms' rule of one account per slot: take the slot back in the console, which wipes it.

A holder wants their slot on another Claude account

It is theirs to do: Change account on their page, on a slot in use. The new account signs in to a scratch directory while the old one keeps working, and replaces it only once that sign-in has finished; the files and paired CC Fleet devices stay. At that point the persistent terminal is restarted so no running Claude process keeps the previous account; the holder runs ccfleet again.

  • Once a week. The next change can come seven days after one that moved the account; signing in with the account the slot already has does not count. Their slot card says when, in their own time zone. There is no override: if it cannot wait, they give the slot back (a wipe) and claim another, which starts with no week behind it.
  • What you see. The Slots card says changed Claude account <age> ago for that week; it never says which account.
  • If it says it stopped halfway. it stopped halfway and could not be undone; change account again to finish it means a step failed and so did putting it back. Changing account again, to the same new account, finishes it; the week has not started.
  • An owner's own node has no Change account: its owner signs it in to whichever account on the node itself, and account_elsewhere still applies.
  • Agents and server ship together. An agent from before Change account hears it as a plain sign-in and refuses the other account, so nothing changes on that slot until its agent is current.

Rebuild a node

  1. New VPS, bootstrap.sh, setup-owner.sh, then restore the latest claude-state-*.tar.gz from ~/backups/ccfleet or the rclone remote. Archive paths are relative to / (home/<owner>/.claude/...), so as the owner run tar -xzf claude-state-<stamp>.tar.gz -C /. It contains no credentials.
  2. Owner runs claude and /login.
  3. server: ccfleetd node rotate-token <node-id> and put the new token in agent.env; the old token is revoked immediately.

Rename a machine

The server's records move first, then the box. Do the two within a few minutes: in between, the box's heartbeats are refused, because a heartbeat names the node its token belongs to and that name has just changed. A refused heartbeat changes nothing on the box (a shared machine provisions, wipes and restarts nothing on one), so the gap costs a report or two, not a slot.

  1. server: ccfleetd node rename <old> <new>. Its slots, heartbeats, alerts and its own sign-in move with it, in one transaction; its token does not change.
  2. server, shared machine only: rename its slot, whatever its state, held and in use included: ccfleetd slot rename <old> <new>. The holder, the claim and the sign-in move with it, and a held slot keeps its holder's name. The machine knows its slot by its Linux user and each claim by its time, never by the slot's id, so the box needs nothing for this. An owner's node counted as their slot is renamed with the node in step 1.
  3. The box's own record of its id: root, on a shared machine, set CCFLEET_NODE_ID=<new> in /etc/ccfleet/agent.env; node, on an owner's node, the same line in ~/.config/ccfleet/agent.env. The next heartbeat is accepted. On a shared machine, stop here: steps 4 and 5 happen by themselves. The machine agent answers to its slot's name (its holder's while held, its own pool name while free): on its next run it rewrites /etc/hosts, runs hostnamectl, writes the cloud-init drop-in, and restarts any legacy Remote Control service if it is running. The console says "hostname pending" until it has. An owner's node is never renamed for you; go on with step 4 there.
  4. root: the host. Put the new name in /etc/hosts before the hostname changes, so sudo never runs on a name it cannot resolve: the line 127.0.1.1 <new> <old> (on some images the old name sits on the public address's line instead; replace it there). Then hostnamectl set-hostname <new>, and keep cloud-init from putting the provider's name back at the next boot: printf 'preserve_hostname: true\nmanage_etc_hosts: false\n' > /etc/cloud/cloud.cfg.d/99-ccfleet.cfg.
  5. On a legacy owner node, Remote Control takes its name from the hostname (--name %H), which systemd fills in when it loads the unit. So, as each user running it (the owner on an owner's node, the signed-in slot on a shared machine): systemctl --user daemon-reload && systemctl --user restart claude-remote-control, or reboot the box, which does both. It keeps its environment and registers again under the new hostname, so claude.ai/code shows the machine by its new name. The session it created on its very first start keeps its old title until it is archived in claude.ai; sessions started since are unaffected. Restarting ends whatever is running in Remote Control, so pick a quiet moment.
  6. server: ccfleetd node list shows the new id with a fresh last seen, and ccfleetd slot list --machine <new> the renamed slots in their old states.

Count an owner's own node as their slot (legacy)

An owner's own node can count as a slot they hold, so everything a person uses is one list on their page and in the console: one account, one slot. It is a record and nothing more. Nothing on the node changes, and ccfleet never hands it out, provisions it or wipes it.

  1. server: it counts toward their allowance like any slot, so raise it first if they are at it: ccfleetd account quota <email> <n>.
  2. server: ccfleetd node hold <node> <email>. Their Linux login on it is taken as the node's owner; name another with --unix-user <login>.
  3. Their page shows the node as their slot, from the node's own heartbeat: signed in or not, the plan and usage. Signing in again runs the node's own sign-in, for them alone. CLI pairing is only offered for hosted machine slots. There is no "Give it back": that would mean wiping somebody's own machine.

Let go of the record with ccfleetd node hold <node> --none; the node, its history and its own sign-in stay exactly as they are.

Keep a machine for one account

A shared machine can be kept for one account, so its free slot never goes to anybody else: your own erik-N machines, or a machine set aside for one customer.

  1. server: ccfleetd node reserve <machine> <email>. The address is the account's, as it signed in; an unknown address is refused, and only a shared machine can be kept.
  2. Claims from that account take a slot on a machine kept for it first; nobody else is ever handed its slot. The account's allowance still applies.
  3. ccfleetd node list shows the reservation in its last column. Customers' pages never show one.

Open it to anybody again with ccfleetd node reserve <machine> --none.

Remove an owner

  1. server: ccfleetd node disable <node-id> (keeps history) or ccfleetd node remove <node-id> (deletes heartbeats and alerts).
  2. Owner runs /logout on the node, then destroy the VPS.

Rotate the admin token

server: change CCFLEET_ADMIN_TOKEN in the env file, restart ccfleetd, update the password saved in your browser.

Upgrade validation

Hosted upgrade validation runs again when the native binary, native version, relay/runtime code or account binding changes. Check the slot's update status and ccfleet doctor --privacy. Pending checks are not a sign-in failure. A reported pass covers the tested generation, not future provider acceptance.

If validation reports an authentication-source or hosted-extension conflict, review the slot's provider overrides and managed/user native configuration. Fleet does not remove the holder's settings or replace credentials to bypass that conflict. Maintenance retains the original credential namespace, uses a clean environment and private probe workspace, and skips unsafe probes. Fix the configuration and let the next bounded check run. An older refresh-token snapshot is not a recovery method for provider-side rotation.

Operational logs contain fixed outcome categories and HTTP route templates, not response text, authorization, request bodies, query values or dynamic path identifiers. Keep private native history and job output separate from support diagnostics. The new policy does not rewrite historical files.
