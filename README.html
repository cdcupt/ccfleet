CC Fleet

Alpha — Early Access. CC Fleet is still being tested and has not launched commercially. The operator has personally used one residential slot with encouraging results; reliability across providers, configurations and multiple users remains unverified. Introductory Alpha prices may change for new purchases or Fleet-credit renewals. Customers confirm the current quote; an already agreed period keeps its agreed price. An existing monthly card plan keeps its confirmed rate when the machine's offer changes. Alpha — 早期体验。CC Fleet 仍在测试，尚未正式商业发布。 运营者亲自试用一个住宅槽位的结果较好，但不同服务商、配置和多用户场景的可靠性仍未验证。 初期价格以后可能随新购买或余额续费调整；用户先确认当前报价，已经约定的服务期保留原约定价格。 主机报价变化，不会改变已有银行卡月付计划确认的价格。

Fleet credit buys one calendar UTC month; each renewal needs another confirmation. Optional Pay monthly card plans start only after explicit agreement and the first Stripe payment, then renew independently until canceled. Existing slots, balances and prepaid time are not enrolled or converted automatically. Your own Claude or Devin subscription, or Anthropic API usage, is paid separately.

Fleet 余额一次只购买按 UTC 计算的一个日历月，每次续费都需另外确认。 可选的按月付款银行卡计划，只有用户明确同意并在 Stripe 完成首笔付款后才会开通， 各槽位独立续费，直到取消。已有槽位、余额和预付费时间不会自动加入或转换。 用户自己的 Claude 或 Devin 订阅，以及 Anthropic API 用量，均需另行付费。

For paid private slots, CC Fleet pairs each user with a dedicated VPS and dedicated exit IP, and that user's own Claude accounts. One holder, one slot, one bound Claude account: no credential pool or shared inference account. A gateway connection can explicitly select several of the holder's own slots; their credentials and subscription limits remain separate.

Hosting update (2026-10-12): the production website, gateway and broker now run on DMIT. Public URLs and existing device pairings are unchanged. The server and broker names below describe their roles, independent of hosting provider.

The primary command, ccfleet local, runs the original Claude Code CLI on the user's computer. Files, tools, settings and conversation history stay in their native local locations. With a saved gateway, the current signed Fleet client sends supported model requests directly over HTTPS using a separate Fleet connection key: 

original Claude Code on laptop: files, tools, history
    → direct HTTPS to the CC Fleet gateway
    → restricted SSH to a selected slot's inference relay
    → Anthropic

The gateway can read model messages and replies. It terminates the laptop's HTTPS connection and routes requests to a selected slot. The slot uses only its own bound account in the paid private-slot route; its Claude credential is never returned to the laptop or gateway. This route starts no local HTTP listener and uses no laptop-side SSH. See the current gateway guide for account selection, safe failover, connection-key management and privacy.

ccfleet local --transport bridge retains the earlier local loopback bridge and pinned inner SSH carried through the WebSocket broker. Only that bridge and the remote-terminal compatibility path keep model content encrypted through the broker. Plain ccfleet remains a remote-terminal command with remote files and persistent tmux. These are distinct transport boundaries, not proof of slot-only agent execution or metadata-free requests.

This implements the requested local-CLI/dedicated-slot relay workflow; it is not a claim of complete CC Host feature parity or zero metadata disclosure. See the gateway release evidence and dated bridge release evidence. The reliability and privacy design explains expiry-driven native renewal, identity minimization, verified TLS, and per-device transport.

Use the trial page's current launch command. It sets ENABLE_TOOL_SEARCH=false CLAUDE_CODE_DISABLE_TERMINAL_TITLE=1 CLAUDE_CODE_DISABLE_THINKING=1 and starts Claude Code with --safe-mode --permission-mode bypassPermissions --disallowedTools WebSearch,WebFetch. This disables customizations, including project instructions, MCP servers and plugins, for this session; built-in coding tools run without approval prompts. Built-in WebSearch and WebFetch make provider requests unsupported by this route, so the command disables those two tools. Saved settings stay unchanged. Safe mode is optional: remove --safe-mode to load customizations, including compatible MCP tools, provided the request fits the supported features and 192 KiB trial limit. To update a saved command, keep its existing private trial key, add any missing options above, and relaunch Claude Code; no replacement key is needed. Claude Code may ask you to accept bypass mode on its first launch.

Trial limits and metering details试用限额与计量细节

The daily allowance is 1,000,000 tokens per account and 10,000,000 tokens shared, reset at 00:00 UTC. Fully metered usage is charged as reported; if only native cache-read metering is missing, up to 20,000 tokens of allowance stay conservatively held for that turn (or the larger known subtotal). This is not an exact token or USD hard cap. One global active turn; daily caps of 200 model turns and 200 reserved runtime minutes per account and shared; a busy worker asks you to wait. Unknown execution or cleanup pauses new work. Paid private slots and their own-provider subscriptions remain separate.

Each admitted model turn reserves 160 runtime seconds, even for a fast reply. A full 200-minute daily budget fits at most 75 such reservations. Tool handoffs and continuations count as separate model turns. The trial page shows personal and shared runtime remaining; unsupported requests rejected before execution do not reserve model runtime. Trial requests including tools/history are at most 192 KiB. Each native turn has a 120-second generation deadline inside a 160-second reservation. Per-account API throttling allows burst three and refills forty requests per minute; key replacement cannot bypass it. Complete input, output, cache-read and cache-creation counts settle actual reported usage including overshoot. The cache-read-only hold needs verified served-model evidence, a valid reply and confirmed process plus full artifact cleanup. Other missing usage, unknown identity, lost execution or uncertain cleanup pauses new work. Ambiguous model sends are never automatically replayed. max_tokens is context, not an upstream enforced output/spending cap.

每日每账号额度为 1,000,000 token，所有用户共享 10,000,000 token，UTC 零点重置。完整计量按已报告用量结算；只缺少原生缓存读取计量时，每轮保守保留最多 20,000 token 额度，已知部分更大则保留更多。这不是精确 token 或美元硬上限。全局同时仅一轮；每个账号及全局共享每日均最多 200 轮、预留 200 分钟；忙碌时请稍候。执行或清理不确定时暂停。付费私人槽位及自有服务商订阅仍独立使用。

每轮模型请求预留 160 秒，即使回复很快也会占用整笔预留。完整的每日 200 分钟最多容纳 75 次此类预留。工具交接和后续回复分别计为模型轮次。试用页显示个人与全局共享的剩余运行时间；执行前被拒绝的不支持请求不会预留模型运行时间。含工具及历史的请求最多 192 KiB；每轮原生生成最多 120 秒，包含在 160 秒预留时间内。账号 API 限流允许瞬时三次、每分钟恢复四十次，更换密钥不能绕过。完整的输入、输出、缓存读取及创建数量按实际报告总数结算，超额也计入。仅缺缓存读取时，必须有已验证模型、有效回复、进程与全部产物已清理的证据，才可保守保留额度。其他计量、身份、执行或清理不确定时暂停新任务；发送情况不确定时绝不自动重放。max_tokens 仅作为上下文，不是上游强制输出或费用上限。

Customer setup and migration

  1. Sign in on the website, claim an allowed slot, and complete Sign in to Claude with your own account. That credential remains on the slot.

  2. Run the same setup command for a new or existing computer:

    curl -fsSL https://raw.githubusercontent.com/cdcupt/ccfleet/main/laptop/install.sh | bash -s -- --setup

  3. Existing pairing and native Claude installation are reused. Setup creates or reuses the saved HTTPS gateway when available. If the original local Claude CLI is missing, setup installs it from the fixed vendor URL. Only if asked, obtain one fresh ten-minute pairing code from Connect this computer on your slot page.

  4. If an older live-folder grant is active, finish its work or explicitly approve stopping its background connector and associated remote live-folder sessions. Setup asks in the controlling terminal; --yes explicitly authorizes this cancellation for scripts. Files/history and ordinary remote tmux sessions are kept. A failed cleanup must be resolved, not silently ignored.

  5. Open a new terminal and run native Claude in your project:

    cd ~/code/my-project
ccfleet start

Setup checks readiness without uploading project files or making a model request. It preserves configuration/history and backs up shell settings when adjusting PATH. Legacy ccfleet-connect cleanup happens only after readiness succeeds. It does not automatically revoke an Anthropic credential: revoke an old setup-token yourself only if it is no longer used anywhere else.

An already paired computer without a saved gateway can run ccfleet gateway setup. A saved gateway is the default for ccfleet local; a failed gateway readiness check does not silently start the bridge. Use ccfleet local --transport bridge only when choosing the compatibility route.

Optional --name "Personal Mac" labels a new device; --slot SLOT chooses an existing pairing. Install-only (omit --setup), manual ccfleet login, and legacy --migrate remain compatibility options. No SSH command or slot Claude credential needs to be entered locally.

ccfleet start offers local new/continue/resume choices; ccfleet local remains the direct launch command. Bare ccfleet has not changed meaning: it still opens the remote terminal. ccfleet remote is the explicit remote alias.

Native local files, sessions and settings

ccfleet local does not upload or mount a folder and adds no filesystem count, size or Git-ignore filters. cd ~ works too. The working directory is not a sandbox: original Claude's native permissions govern local file and tool access. New conversations default to bypassPermissions, Opus and max effort, so local tools can modify, delete or transmit data without individual approval prompts.

ccfleet local --check
ccfleet local --new --name work
ccfleet local --new --name research --permission-mode plan --model opus --effort high
ccfleet local --resume
ccfleet local --resume work
ccfleet local --continue
ccfleet local --resume work --fork-session
ccfleet local --print "Summarize this project"
ccfleet sessions
ccfleet preferences set --model opus --effort high --permission-mode plan
ccfleet preferences show
ccfleet preferences clear

Running plain ccfleet local again starts a fresh conversation in the current directory; it does not automatically resume the previous one. Use --continue for the latest conversation in that directory, or --resume for the history picker. Existing history is kept. A second terminal opens an independent local session using the same assigned slot/account.

These are native local conversations, not remote tmux sessions. Use /model and /effort in Claude; availability depends on the installed CLI and account. Additional supported native arguments go after --, subject to protected routing/authentication settings. Quit normally with /exit; resume saved local history later. CC Fleet does not silently replay interrupted inference. Interactive foreground sessions, --print, --resume, and multiple terminal sessions are supported. ccfleet sessions opens native history; project preferences affect new local sessions, with explicit flags taking precedence. They do not rewrite existing conversations or synchronize history between computers.

Existing standard old-domain profiles use the new address without replacing saved keys, pairings, slot choices or provider settings. Existing 0.2.5 processes keep working through the compatibility address.

Diagnostics, signed updates and background work

ccfleet status --json
ccfleet doctor --privacy --json --export ./ccfleet-support.json
ccfleet version --json
ccfleet update
ccfleet update --rollback

Diagnostics make no model request and do not scan a project. Export creates only the requested new private local file; it is not uploaded and excludes prompts, file contents, paths, tokens and account emails. Reported account health separates ready, renewal pending, sign-in required, account maintenance and stale observations. A heartbeat does not prove that Anthropic will accept the next model request.

The updater authenticates its signed release channel using the pinned Ed25519 key, then checks the immutable manifest and every digest-pinned helper before atomic activation. Failed verification leaves the current client in place. Rollback preserves pairing and native history; restored legacy bootstraps are not labelled signature-verified. version --json distinguishes verified and bootstrap installs. This updates CC Fleet, not the original Claude executable.

ccfleet jobs start --prompt "Review this project and summarize findings"
ccfleet jobs list
ccfleet jobs status JOB_ID
ccfleet jobs logs JOB_ID
ccfleet jobs stop JOB_ID
# Equivalent supervised launch:
ccfleet local --background --print "Summarize this project"

These are managed local print-mode jobs, not native detached --bg, remote agents or interactive attachable sessions. Jobs use the configured default model route and pin the starting slot, so gateway backup switching is disabled for that job. The supervisor owns the native process and any bridge transport after the starting terminal closes; the computer must stay running and connected. Use an explicit --resume NAME_OR_ID or --continue for existing context. Passing native --bg / --background after -- remains rejected.

Jobs default to one hour (--timeout, maximum 24 hours) and four concurrent jobs (--max-jobs, maximum 16). Private stdout/stderr logs are each bounded to 4 MiB; they may contain sensitive content and are displayed only on request. Stop, timeout, revocation and supervisor loss close the owned process group and transport; uncertain cleanup is reported as such. Deliberately detached tool processes are not sandbox-contained. Jobs never automatically restart or replay inference.

Native settings/history, including an existing CLAUDE_CONFIG_DIR, are preserved by default. --legacy-history selects the earlier per-slot relay-preview profile without importing or deleting it. A temporary private settings overlay pins the selected model route and authentication, clears conflicting provider/auth overrides, and disables supported optional telemetry without permanently editing native settings. Gateway launches use the saved HTTPS URL and Fleet connection key; explicit bridge launches use the loopback endpoint and launch-scoped nonce.

The previous live-folder mount is retired. ccfleet local --disconnect remains an explicit cleanup action for it; --reset-link is retired. Earlier snapshot commands are only for recovery. See local relay and migration for shutdown-error recovery and a safe local-file check, and retired workspaces. The current user guide is at /docs/guide.

Privacy and routing scope

Client 0.2.2 adds opt-in local read-only management MCP via ccfleet mcp serve: cached health, native quota observations and numeric relay usage. Tools expose their stated fixed codes/numbers to the calling AI, not account/device identities, hosts/IPs, local paths, prompts or logs. No automatic registration, project scan, model request, quota refresh or mutation. See setup and disclosure boundaries.

The relay removes selected headers and the top-level structured metadata field. It does not redact arbitrary prompts or tool results. Native system prompts can include OS, working-directory and environment details; file contents and paths can identify users and reach the gateway, selected slot and Anthropic. Do not claim fingerprint-free requests or that Anthropic sees only slot information.

Only supported model endpoints use the relay. MCP servers, hooks, plugins, shell tools, updates and other native CLI services can connect directly from the laptop. Optional telemetry controls are not an all-traffic firewall or anonymity guarantee. The gateway sees connection IP/transport metadata and model contents. Gateway and slot administrators can inspect or alter requests/responses, which can influence local tool actions. In the explicit SSH bridge, the broker sees connection metadata but cannot decrypt the inner SSH stream. Native local permissions and trust in the gateway and slot hosts remain important.

Relay access requires upgraded nodes and operator activation. A previous remote terminal or live-mount deployment does not establish relay availability or provider authorization; validate the canary and actual deployment separately. The compliance record distinguishes the historical hosted terminal mapping from the current inference relay; it makes no approval claim.

Remote-terminal compatibility

Plain ccfleet still opens original Claude Code on the slot, with projects in ~/workspace and persistent tmux. The default remains Opus, max effort and bypassPermissions, as the slot Linux user. Named remote sessions remain:

ccfleet new research --model fable --effort xhigh --permission-mode plan
ccfleet attach --session research
ccfleet restart --session research --model opus --effort max --permission-mode auto

These commands do not operate on local Claude conversation history. An intentional remote restart terminates that session before replacing it.

What runs where

  • laptop/ccfleet starts native local Claude using the saved direct HTTPS gateway. It retains the explicit local bridge and remote-terminal compatibility commands.
  • ccfleetd/gateway.py handles authenticated Messages API requests and safe routing among explicitly selected own slots; it can read model bodies and replies.
  • ccfleet_agent/inference_client.py implements the legacy authenticated local bridge; ccfleet_agent/local_relay.py handles fixed-upstream slot inference.
  • ccfleetd/ also handles the website, pairing, device authorization, operational state and encrypted byte broker. Slot Claude credentials stay on their slots; the broker's opaque SSH boundary does not apply to the HTTPS gateway.
  • ccfleet_agent/machine.py manages slot users and root-owned device keys.
  • node/slot-entry.sh dispatches only fixed protocols with forwarding disabled.
  • project_files.py, project_access.py, and the live-folder helpers retain legacy recovery/cleanup responsibilities; they are not the local agent.

Server quickstart

For a new deployment, run the primary ccfleetd service behind TLS:

git clone https://github.com/cdcupt/ccfleet.git
cd ccfleet
cp deploy/ccfleetd.env.example deploy/ccfleetd.env
# Set CCFLEET_ADMIN_TOKEN, CCFLEET_PUBLIC_URL, Google OAuth and cookie secrets.
docker compose -f deploy/docker-compose.yml up -d --build

For host-installed Caddy, adapt deploy/Caddyfile.example with the public hostname. It forwards HTTPS traffic to the service's loopback port 127.0.0.1:8110. Validate the active host Caddy configuration, then reload the host Caddy service. Use DNS-only records for direct gateway HTTPS. The optional secondary byte-broker overlay is deploy/broker-compose.yml. deploy/broker-caddy.example uses Docker service names and requires Caddy to join the same private Compose network. For host-installed Caddy, adapt that example's upstreams to 127.0.0.1:8110 for the primary and 127.0.0.1:8113 for the broker. Keep the named Fleet access/error log discard in either topology.

Run server administration commands inside the running primary container so they use its live environment and mounted SQLite database. The examples below use the repository Compose layout. For an existing deployment, use its active Compose file and project; see the platform migration runbook. A separate host-native CLI invocation can otherwise create or modify a different local database.

The bare public URL serves the product website. /account is the customer page; /admin is the operator console. CCFLEET_ADMIN_HOST can move the console to a separate hostname.

Create a shared machine and its slots:

docker compose -f deploy/docker-compose.yml exec ccfleetd ccfleetd node add pool-1 --owner ops --region us-west
docker compose -f deploy/docker-compose.yml exec ccfleetd ccfleetd slot add pool-1 --machine pool-1 --unix-user slot01

On a fresh Ubuntu machine, first install base hardening and then the shared machine agent:

git clone https://github.com/cdcupt/ccfleet.git
sudo ./ccfleet/node/bootstrap.sh ops "ssh-ed25519 AAAA... operator"
sudo hostnamectl set-hostname pool-1
sudo timedatectl set-timezone Etc/UTC

curl -fsSL https://raw.githubusercontent.com/cdcupt/ccfleet/main/node/machine-setup.sh \
  | sudo bash -s -- \
      --server https://fleet.example.com \
      --node pool-1 \
      --token <node-token>

Configure the fixed endpoint the CC Fleet server uses to reach that machine. Copy the node's public SSH host key over an authenticated operator channel to a readable file inside the primary container, for example /data/pool-1-ssh_host_ed25519_key.pub:

docker compose -f deploy/docker-compose.yml exec ccfleetd ccfleetd node access pool-1 \
  --host <address-reachable-from-server> \
  --port 22 \
  --host-key-file /data/pool-1-ssh_host_ed25519_key.pub

Only the CC Fleet server needs network access to the node's SSH port. The customer uses the public HTTPS/WSS service and never receives the node address.

Grant a signed-in customer an allowance:

docker compose -f deploy/docker-compose.yml exec ccfleetd ccfleetd account quota alice@example.com 1
docker compose -f deploy/docker-compose.yml exec ccfleetd ccfleetd account role you@example.com admin

Lifecycle rules

  • A slot is offered only after its machine confirms the previous Linux user is absent.
  • Releasing a slot immediately revokes all paired CC Fleet devices, stops its processes and deletes the Linux user and files. The slot becomes free only after the machine confirms the wipe.
  • A slot keeps one Claude account. Sign in again accepts only that account; Change account replaces it deliberately and at most once a week.
  • One Claude account detected on two live fleet slots raises an alert.
  • Lowering an allowance does not seize an existing slot.
  • Payments are records for the operator; the allowance remains the grant.
  • Claude Code updates are staged and never interrupt the running persistent session. New sessions use the installed version.

The public site documents the current product at /, /docs/guide, /docs/how-it-works, /docs/terms and /privacy.

Security and privacy boundary

For the current HTTPS gateway, TLS protects each connection in transit. The gateway decrypts model requests and replies and reaches the selected slot through restricted, host-pinned SSH. The Fleet connection key is independently revocable and distinct from the slot's Claude credential. See gateway privacy and connection-key management.

The following controls describe the explicit SSH bridge and remote-terminal compatibility path:

  • The outer connection is TLS/WSS to the broker.
  • The inner OpenSSH connection is encrypted end-to-end and pins the slot host key returned at pairing.
  • Device keys live outside holder-writable home directories. Both sshd and each key enforce the forced entrypoint, with no agent forwarding, port forwarding, X11 forwarding or user-supplied SSH command.
  • The public-key path is root-owned but readable by slot users (0711 parent, 0755 key directory, 0644 files); the node token remains in an atomically written root-only 0600 file.
  • Slot accounts receive a discarded random password only so OpenSSH/PAM will evaluate public keys; the slot sshd policy explicitly disables password and keyboard-interactive authentication.
  • Pairing codes are random, single-use, stored only as hashes and expire after ten minutes.
  • Device access tokens are random and stored only as hashes. Device removal or slot release revokes them immediately.
  • The broker chooses the node endpoint from operator configuration; the client cannot use it as an arbitrary TCP proxy.
  • The local client stores its private key and access token under ~/.config/ccfleet with mode 0600.
  • The slot administrator still has root. End-to-end transport encryption does not hide plaintext model requests/responses from the slot relay endpoint.

Rental slots publish separate hosting and IP-provider brands and a per-machine monthly USD rate under Alpha pricing. ISP and Residential are network types, with the same formula and no separate residential premium. Neither type guarantees quality, speed or Claude compatibility. Monthly resource cost is the recorded VPS plus exit-IP cost normalized to a calendar month. Annual costs divide by 12; 30-day costs multiply by 365/360. Convert any non-USD supplier invoice before entry and retain the FX rate and date in private operator records; the application does not invent exchange rates. Missing costs or costs not converted to USD make pricing unavailable.

Round normalized USD resource cost half up to cents. The monthly service fee is the greater of $2 or 10% of that rounded cost, rounded half up to cents. Add the displayed resource cost and service fee to obtain the monthly customer total. Examples: $8.68 + $2 = $10.68; $10.83 + $2 = $12.83; $22.28 + $2.23 = $24.51; $27.44 + $2.74 = $30.18. The $2 fee applies through $20 of resource cost. The public breakdown shows VPS cost, separately recorded exit-IP cost, service fee and total; a bundled hosting-and-IP cost is shown as a bundle without an invented split. A normalization rounding line explains any cent-level difference between individually displayed components and the rounded combined resource cost.

Open Available slots, choose a machine and review its price. A Fleet-credit purchase pays once for one calendar UTC month; the customer confirms each renewal. The optional Pay monthly card plan requires explicit agreement and the first Stripe payment. Each slot renews independently at its confirmed rate until canceled; a changed machine offer does not reprice an existing plan. Existing holders are not enrolled automatically. Your own Claude or Devin subscription, or Anthropic API usage, remains separate.

Approved proxy nodes use a protected local CONNECT service and verified provider TLS; proxy credentials stay in root-only configuration. See the provider, pricing and egress runbook.

Retired or disabled machines are omitted from the public rental inventory and normal operator catalogue. This does not release an existing holder or delete accounts, payments or history. Enabled machines with a temporary outage still appear on Status, so an outage is visible instead of being treated as retirement. Configuring a price never rewrites past payments or includes a Claude subscription.

Operations

Agents report heartbeat facts and the server raises alerts for missing nodes, missing or stale Claude login, version drift, disk pressure and changed egress. Legacy owner-node and Remote Control monitoring remains in the code for owner installations. Hosted customer slots actively disable the old Remote Control unit; it is not an alternative product mode.
